# 故障排查指南

> 启动顺序与环境见 [[本地启动指南]]；登录/token 见 [[登录与鉴权指南]]。  
> **监控告警联读**：先 [[监控与日志]] 看告警/健康探测/ERROR 日志落在哪服务，再回本页决策树。

面向茉莉微服务**本地联调与常见生产问题**的快速决策树。登录/鉴权专项对照表见 [[茉莉登录与鉴权故障根因汇总]]。

## 0. 和监控告警怎么配合

1. 有 **监控告警 / 健康探测失败 / 日志 ERROR** → 打开 [[监控与日志]]，确认服务与信号。  
2. 对照本页对应章节（登录鉴权、Dubbo、CORS…）做动作。  
3. 登录类专项 → [[茉莉登录与鉴权故障根因汇总]]。

## 1. 登录 / 鉴权 500 或失败

| 现象 | 优先检查 |
|------|----------|
| 登录 500，日志 Redis 连接 refused | **Redis 未启动**（16379）→ 启动 Redis |
| 登录成功但跨服务 401 | 各服务 **Redis host/port/password/database 不一致** → 对齐 `application-dev.yml` |
| token 无效 | Header 是否为 `Authorization: <sessionId>`，见 [[登录与鉴权指南]] |
| 权限不足 403 | RBAC 角色菜单，见 [[权限管理操作指南]] |

Session 机制见 [[认证与会话机制]]；Redis 角色见 [[茉莉-缓存-多级]]。

## 2. 服务注册 / Dubbo 调用失败

| 现象 | 优先检查 |
|------|----------|
| Nacos 无实例 | Nacos 是否启动（Docker **28548** 或 **8848**）；`namespace=dev` |
| Dubbo No provider | [[用户中心]] 是否先启动；`group=moli` `version=1.0.0` 一致 |
| Gateway 404 | 路径前缀 `/UserCenter/` 等是否正确；网关是否最后启动 |

详见 [[茉莉-nacos-dev命名空间]]、[[茉莉-dubbo-group版本]]。

## 3. 数据库相关

| 现象 | 优先检查 |
|------|----------|
| 连接失败 | MySQL 8 是否启动；库名 `moli`；账号密码 |
| 表不存在 | 是否执行 `scripts/moli.sql` + 秒杀/知识库增量 SQL |
| 慢 / 池耗尽 | Druid 连接池配置是否生效；慢 SQL 索引见 `moli-knowledge/kb/wiki/database/mysql-索引.md` |
| 登录用户不存在 | 是否导入 baseline 用户；`reset-demo-passwords.sql` |

## 4. 秒杀 / 订单异常

| 现象 | 优先检查 |
|------|----------|
| 库存不准 | Redis 预热脚本；Lua 脚本是否执行 |
| 订单未落库 | 消费者线程是否运行；Redis 队列积压 |

见 [[秒杀设计]]、[[订单服务]]。

## 5. JVM / 进程

| 现象 | 处理 |
|------|------|
| OOM / Metaspace | `moli-knowledge/kb/wiki/java/jvm-oom与排查入门.md`：jmap dump + MAT |
| CPU 100% | jstack 定位线程；是否 Full GC 死循环 → [[故障排查指南]] |
| 端口占用 | `netstat` / 改 `server.port` |

## 6. 推荐排查顺序

```
1) 基础设施三件套：Nacos + MySQL + Redis 全活
2) user-center 注册成功且 HTTP 28101 可访问
3) 业务服务 + Dubbo 调通
4) Gateway 28100 转发
5) 前端 / Postman 带 token 调接口
```

## 7. 日志与 Loki

| 现象 | 优先检查 |
|------|----------|
| Grafana 查不到日志 | 时间范围是否覆盖日志行时间；**关掉 Live**；见 [[监控与日志]] §3 |
| 只有启动日志、无业务日志 | logback 是否写 FILE；MyBatis 是否 `Slf4jImpl`（非 StdOutImpl） |
| SQL 搜不到 | 勿固定 `level=INFO`；用 `\|= "Preparing"` 或 DEBUG |
| 故障诊断 500 | **moli-aiops** 是否在 **28105** 运行（Vite 代理，非 Java log） |
| 控制台有 SQL、Loki 没有 | 控制台 stdout ≠ 落盘；看模块 `logs/{service}.log` |

各服务 log 路径与 Loki 标签见 [[监控与日志]] §1。

## 8. Prometheus / Actuator（Shiro 服务）

| 现象 | 根因 | 立即动作 |
|------|------|----------|
| `/actuator/*` 返回 `10006 请登录`（knowledge/order/ai） | starter 曾 `@Bean AuthenticationFilter` → Boot 全局 Servlet Filter 绕过 Shiro anon | Rebuild **`moli-user-center-shiro-starter`** + 服务并重启；见 [[茉莉-shiro-跨服务]] §4 |
| `.m2` JAR 已有 `/actuator/**` 仍 10006 | 同上，非 JAR 版本问题 | 同上，勿只 reinstall JAR |
| user-center 28101 正常，28104 异常 | user-center 用 `new AuthenticationFilter()`，未暴露 Bean | 对照 [[茉莉-shiro-跨服务]] §3 |
| Prometheus Target **connection refused** | order/ai/knowledge 未启动 | IDEA 启动对应 `(dev)` 配置 |
| Target UP 但 scrape 报错 *invalid format* | 仍返回 JSON 10006 | 先修 Shiro，再 `restart prometheus` |
| 改 `prometheus.yml` 后 Target 不变 | Prometheus 未重载配置 | `docker compose -f deploy/observability/docker-compose.observability.yml restart prometheus` |

验证命令（PowerShell）：

```powershell
curl.exe -s http://127.0.0.1:28104/actuator/health
curl.exe -s http://127.0.0.1:28104/actuator/prometheus | Select-Object -First 3
```

工程详述：`docs/ops/monitoring-and-logs.md` §4.3 · [[监控与日志]]。

## 9. 日志位置（传统）

各服务 **log 文件**在模块 `logs/`（IDEA 工作目录须为仓库根）。临时 Spring `debug: true` 仅排查自动配置，勿长期开启。
