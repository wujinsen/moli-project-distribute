# 分布式锁（概念枢纽）

> 本页是「分布式锁」主题的枢纽。面试速记见 [[分布式锁面试题]]；Redis 实现演进与正确姿势见 [[redis分布式锁实现]]；本项目秒杀也用到 Redis 原子操作，见 [[秒杀设计]]。

## 为什么需要分布式锁？

单机下用 `synchronized` / `ReentrantLock` 即可，但它们**只在同一个 JVM 进程内有效**。分布式集群有多个 JVM 进程，需要一个**外部中间人**来协调，保证同一时刻只有一个进程的一个线程能操作共享资源。

## 一个合格的分布式锁要满足

| 特性 | 说明 |
|------|------|
| **互斥** | 任意时刻只有一个客户端持有锁 |
| **防死锁** | 客户端崩溃也能最终释放（通常靠超时机制） |
| **可重入** | 同一线程可重复获取，避免自死锁 |
| **高可用/容错** | 锁服务集群化，部分节点挂了仍可用 |
| **高性能** | 加锁/解锁开销小 |
| **安全释放** | 只有持有者能释放自己的锁（防误删） |

## 三种实现方案对比

| 维度 | 数据库 | 缓存（Redis） | ZooKeeper |
|------|--------|---------------|-----------|
| 实现方式 | 唯一索引 `insert` / `select ... for update` 行锁 | `SET k v NX PX` + Lua 释放 | 临时顺序节点 + 监听前驱 |
| 理解难度 | 低 | 中 | 高 |
| 实现复杂度 | 低 | 中 | 中高 |
| **性能** | 低 | **高** | 中 |
| **可靠性** | 低 | 中 | **高**（临时节点天然防死锁） |
| 典型坑 | 单点、无超时、行锁可能退化表锁 | 误删、超时续期、主从切换丢锁 | 性能略低、羊群效应 |

- **数据库**：唯一索引插入（存在即加锁）或 `for update` 排他锁；注意 `method_name` 要加**唯一索引**，否则 InnoDB 可能用表锁。
- **Redis**：性能最好、最常用，但要处理误删/续期/主从问题，细节见 [[redis分布式锁实现]]。
- **ZooKeeper**：临时顺序节点 + watch 前驱，客户端掉线自动删节点防死锁；可靠性最高，常用 Curator 的 `InterProcessMutex`。

## 选型建议（按使用目的）

- **效率（Efficiency）场景**：偶尔重复执行也无大碍 → 用相对宽松的 Redis 锁即可，保证活性。
- **正确性（Correctness）场景**：绝不允许两个客户端同时持锁/操作 → 选 ZooKeeper 或 Redlock，并在业务上做**幂等**兜底（因为没有绝对安全的分布式锁）。
