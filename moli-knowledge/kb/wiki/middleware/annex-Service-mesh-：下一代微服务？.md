## Service Mesh：下⼀代微服务？

2017-1-02敖⼩剑

![image 1](assets/imageFile1.png)

作者｜敖⼩剑

微服务⽅兴未艾如⽕如荼之际，在 spring cloud 等经典框架之外，Service Mesh 技术正在悄然兴起。到底什 么是 Service Mesh，它的出现能带来什么，⼜能改变什么？本⽂整理⾃数⼈云资深架构师敖⼩剑在 QCon 2017 上海站上的演讲。 简单回顾⼀下过去三年微服务的发展历程。在过去三年当中，微服务成为我们的业界技术热点，我们看到⼤ 量的互联⽹公司都在做微服务架构的落地。也有很多传统企业在做互联⽹技术转型，基本上还是以微服务和 容器为核⼼。 在这个技术转型中，我们发现有⼀个⼤的趋势，伴随着微服务的⼤潮，Spring Cloud 微服务开发框架⾮常普 及。⽽今天讲的内容在 Spring Cloud 之外，我们发现最近新⼀代的微服务开发技术正在悄然兴起，就是今天 要给⼤家带来的 Service Mesh/ 服务⽹格。 我做⼀个⼩⼩的现场调查，今天在座的各位，有没有之前了解过服务⽹格的，请举⼿。（备注：调查结果， 现场数百⼈仅有 3 个⼈举⼿）

既然⼤家都不了解，那我来给⼤家介绍。⾸先，什么是 Service Mesh？然后给⼤家讲⼀下 Service Mesh 的 演进历程，以及为什么选择 Service Mesh 以及为什么我将它称之为 下⼀代的微服务，这是我们今天的内 容。

# 1什么是Service Mesh？

我们⾸先说⼀下 Service Mesh 这个词，这确实是⼀个⾮常⾮常新的名词，像刚才调查的，⼤部分的同学都没 听过。

![image 2](assets/imageFile2.png)

这个词最早使⽤由开发 Linkerd 的 Buoyant 公司提出，并在内部使⽤。2016 年 9 ⽉ 29 ⽇第⼀次公开使⽤这 个术语。2017 年的时候随着 Linkerd 的传⼊，Service Mesh 进⼊国内技术社区的视野。最早翻译为“服务啮 合层”，这个词⽐较拗⼝。⽤了⼏个⽉之后改成了服务⽹格。后⾯我会给⼤家介绍为什么叫⽹格。

![image 3](assets/imageFile3.png)

先看⼀下 Service Mesh 的定义，这个定义是由 Linkerd 的 CEO Wiliam 给出来的。Linkerd 是业界第⼀个 Service Mesh，也是他们创造了 Service Mesh 这个词汇的，所以这个定义⽐较官⽅和权威。 我们看⼀下中⽂翻译，⾸先服务⽹格是⼀个基础设施层，功能在于处理服务间通信，职责是负责实现请求的 可靠传递。在实践中，服务⽹格通常实现为轻量级⽹络代理，通常与应⽤程序部署在⼀起，但是对应⽤程序 透明。 这个定义直接看⽂字⼤家可能会觉得⽐较空洞，不太容易理解到底是什么。我们来看点具体的东⻄。

![image 4](assets/imageFile4.png)

Service Mesh 的部署模型，先看单个的，对于⼀个简单请求，作为请求发起者的客户端应⽤实例，会⾸先⽤ 简单⽅式将请求发送到本地的 Service Mesh 实例。这是两个独⽴进程，他们之间是远程调⽤。 Service Mesh 会完成完整的服务间调⽤流程，如服务发现负载均衡，最后将请求发送给⽬标服务。这表现为 Sidecar。

![image 5](assets/imageFile5.png)

##### Sidecar 这个词中⽂翻译为边⻋，或者⻋⽃，也有⼀个乡⼟⽓息浓重的翻译叫做边三轮。Sidecar 这个东⻄出 现的时间挺⻓的，它在原有的客户端和服务端之间加多了⼀个代理。

![image 6](assets/imageFile6.png)

多个服务调⽤的情况，在这个图上我们可以看到 Service Mesh 在所有的服务的下⾯，这⼀层被称之为 服务 间通讯专⽤基础设施层。Service Mesh 会接管整个⽹络，把所有的请求在服务之间做转发。在这种情况下， 我们会看到上⾯的服务不再负责传递请求的具体逻辑，只负责完成业务处理。服务间通讯的环节就从应⽤⾥ ⾯剥离出来，呈现出⼀个抽象层。

![image 7](assets/imageFile7.png)

如果有⼤量的服务，就会表现出来⽹格。图中左边绿⾊⽅格是应⽤，右边蓝⾊的⽅框是 Service Mesh，蓝⾊ 之间的线条是表示服务之间的调⽤关系。Sidecar 之间的连接就会形成⼀个⽹络，这个就是服务⽹格名字的由 来。这个时候代理体现出来的就和前⾯的 sidecar 不⼀样了，形成⽹状。

![image 8](assets/imageFile8.png)

再来回顾前⾯给出的定义，⼤家回头看这四个关键词。⾸先第⼀个，服务⽹格是抽象的，实际上是抽象出了 ⼀个基础设施层，在应⽤之外。其次，功能是实现请求的可靠传递。部署上体现为轻量级的⽹络代理。最后 ⼀个关键词是，对应⽤程序透明。

⼤家注意看，上⾯的图中，⽹络在这种情况下，可能不是特别明显。但是如果把左边的应⽤程序去掉，现在 只呈现出来 Service Mesh 和他们之间的调⽤，这个时候关系就会特别清晰，就是⼀个完整的⽹络。这是 Service Mesh 定义当中⼀个⾮常重要的关键点，和 Sidecar 不相同的地⽅：不再将代理视为单独的组件，⽽ 是强调由这些代理连接⽽形成的⽹络。在 Service Mesh ⾥⾯⾮常强调代理连接组成的⽹络，⽽不像 sidecar 那样看待个体。 现在我们基本上把 Service Mesh 的定义介绍清楚了，⼤家应该可以⼤概了解什么是 Service Mesh 了。

# 2Service Mesh 演进历程

第⼆个部分和⼤家追溯⼀下 Service Mesh 的演进历程。要注意，虽然 Service Mesh 这个词汇直到 2016 年 9 才有，但是它表述的东⻄很早以前就出现了。

![image 9](assets/imageFile9.png)

⾸先看“远古时代”，第⼀代⽹络计算机系统，最早的时候开发⼈员需要在⾃⼰的代码⾥处理⽹络通讯的细节 问题，⽐如说数据包顺序、流量控制等等，导致⽹络逻辑和业务逻辑混杂在⼀起，这样是不⾏的。接下来出 现了 TCP/IP 技术，解决了流量控制问题，从右边的图上可以看到，功能其实没发⽣变化：所有的功能都在， 代码还是要写。但是，最重要的事情，流程控制，已经从应⽤程序⾥⾯抽出来了。对⽐左右两边的图，抽出 来之后被做成了操作系统⽹络层的⼀部分，这就是 TCP/IP，这样的话应⽤的结构就简单了。 现在写应有，就不⽤考虑⽹卡到底怎么发。在 TCP/IP 之后，这是完全不需要考虑的。上⾯说的是⾮常遥远的 事情，⼤概发⽣在五⼗年前。

![image 10](assets/imageFile10.png)

微服务时代也⾯临着类似的⼀些东⻄，⽐如说我们在做微服务的时候要处理⼀系列的⽐较基础的事情，⽐如 说常⻅的服务注册、服务发现，在得到服务器实例之后做负载均衡，为了保护服务器要熔断 / 重试等等。这些 功能所有的微服务都跑不掉，那怎么办呢？只能写代码，把所有的功能写进来。我们发现最早的微服务⼜和 刚才⼀样，应⽤程序⾥⾯⼜加上了⼤量的⾮功能性的代码。为了简化开发，我们开始使⽤类库，⽐如说典型 的 Netflix OS 套件。在把这些事情做好以后，开发⼈员的编码问题就解决了：只需要写少量代码，就可以把 这些功能实现。因为这个原因，最近这些年⼤家看到 Java 社区 Spring Cloud 的普及程度⾮常快，⼏乎成为 了微服务的代名词。 到了这个地步之后，完美了吗？当然，如果真的完美了，那我今天就不会站在这⾥了:)

![image 11](assets/imageFile11.png)

我们看这⼏个被称之为痛点的东⻄: 内容⽐较多，⻔槛⽐较⾼。调查⼀下，⼤家学 Spring Cloud，到你能熟练 掌握，并且在产品当中应⽤，可以解决出现的问题，需要多⻓时间？⼀个星期够不够？⼤部分⼈⼀个星期是 不够的，⼤部分⼈需要三到六个⽉。因为你在真实落地时会遇到各种问题，要能⾃⼰解决的话，需要的时间 是⽐较⻓的。这⾥是 Spring Cloud 的常⻅⼦项⽬，只列出了最常⻅的部分，其中 spring cloud netflix 下还有 netflix OS 套件的很多内容。要真正吃透 Spring Cloud，需要把这些东⻄全部吃透，否则遇到问题时还会⾮ 常难受。 这么多东⻄，在座的各位相对来说学习能⼒⽐较强⼀点，可能⼀个⽉就搞定了，但是问题是你的开发团队， 尤其是业务开发团队需要多久，这是⼀个很要命的事情：业务团队往往有很多⽐较初级的同事。

![image 12](assets/imageFile12.png)

然后事情并不⽌这么简单，所谓雪上加霜，我们还不得不⾯对⼀堆现实。

⽐如说，我们的业务开发团队的强项是什么？最强的会是技术吗？不，通常来说我们的业务开发团队最强 的是对业务的理解，是对整个业务体系的熟悉程度。 第⼆个事情，业务应⽤的核⼼价值是什么？我们⾟⾟苦苦写了这么多的微服务，难道是为了实现微服务 吗？微服务只是我们的⼿段，我们最终需要实现的是业务，这是我们真正的⽬标。 第三个事情是，就微服务这个⼿段⽽⾔，有⽐学习微服务框架更艰巨的挑战。在做微服务的真正落地时， 会有更深刻的理解。⽐如微服务的拆分，⽐如要设计⼀个良好的 API，要保持稳定并且易于扩展，还有如 果涉及到跨多个服务的数据⼀致性，⼤部分团队都会头疼。最后是康威定律，但凡做服务的同学最终都会 遇到这个终极问题，⽽⼤多数情况下是欲哭⽆泪。

但是这些还没完，⽐你写⼀个新的微服务系统更痛苦的事情，是你要对旧有的系统进⾏微服务改造。 所有这些加在⼀起，还不够，还要再加⼀条，这条更要命：业务开发团队往往业务压⼒⾮常⼤，时间⼈⼒永 远不⾜。说下⽉上线就是下⽉上线，说双⼗⼀促销就不会推到双⼗⼆。⽼板是不会管你有没有时间学习 spring cloud 的，也不会管你的业务团队能否搞得定微服务的⽅⽅⾯⾯。业务永远看的是结果。

![image 13](assets/imageFile13.png)

第⼆个痛点，功能不够，这⾥列出了服务治理的常⻅功能。⽽ Spring Cloud 的治理功能是不够强⼤的，如果 把这些功能⼀⼀应对做好，靠 Spring Cloud 直接提供的功能是远远不够的。很多功能都需要你在 Spring Cloud 的基础上⾃⼰解决。 问题是你打算投⼊多少时间⼈⼒资源来做这个事情。有些⼈说我⼤不了有些功能我不做了，⽐如灰度，直接 上线好了，但是这样做代价蛮⾼的。

![image 14](assets/imageFile14.png)

第三个痛点，跨语⾔。微服务在刚开始⾯世的时候，承诺了⼀个很重要的特性：就是不同的微服务可以采⽤ ⾃⼰最擅⻓最喜欢的最适合的编程语⾔来编写，这个承诺只能说有⼀半是 OK 的，但是另外⼀半是不⾏的， 是假的。因为你实现的时候，通常来说是基于⼀个类库或者框架来实现的，⼀旦开始⽤具体编程语⾔开始编 码的时候你就会发现，好像不对了。为什么？左边是我从编程语⾔排⾏列表列出来的主流编程语⾔，排在前 ⾯的⼏种，⼤家⽐较熟悉. 后⾯还有⼏⼗种没有列出来，中间是新兴的编程语⾔，⽐较⼩众⼀点。 现在的问题在于 我们到底要为多少种语⾔提供类库和框架。 这个问题⾮常尖锐，为了解决这个问题，通常只有两条路可选：

1. ⼀种就是统⼀编程语⾔，全公司就⽤⼀种编程语⾔

2. 另外⼀个选择，是有多少种编程语⾔就写多少个类库

我相信在座的如果有做基础架构的同学，就⼀定遇到过这个问题。

![image 15](assets/imageFile15.png)

但是问题还没完，框架写好了，也有能够把各个语⾔都写⼀份。但是接下来会有第四个痛点：版本升级。 你的框架不可能⼀开始就完美⽆缺，所有功能都⻬备，没有任何 BUG，分发出去之后就再也不需要改动，这 种理想状态不存在的。必然是 1.0、2.0、3.0 慢慢升级，功能逐渐增加，BUG 逐渐被修复。但是分发给使⽤ 者之后，使⽤者会不会⽴⻢升级？实际上做不到的。 这种情况下怎么办，会出现客户端和服务器端版本不⼀致，就要⾮常⼩⼼维护兼容性，然后尽量督促你的使 ⽤者：我都是 3.0 了，你别⽤ 1.0 了，你赶紧升级吧。但是如果如果他不升级，你就继续忍着，然后努⼒解决 你的版本兼容性。 版本兼容性有多复杂？服务端数以百计起，客户端数以千计起，每个的版本都有可能不同。这是⼀个笛卡尔 乘积。但是别忘了，还有⼀个前⾯说的编程语⾔的问题，你还得再乘个 N！ 设想⼀下框架的 Java1.0 客户端访问 node.js 的 3.0 的服务器端会发⽣什么事情，c+ 的 2.0 客户端访问 golang 的 1.0 服务器端会如何？你想把所有的兼容性测试都做⼀遍吗？这种情况下你的兼容性测试需要写多 少个 case，这⼏乎是不可能的。

第⼀个是这些问题的根源在哪⾥：我们做了这么多痛苦的事情，⾯临这么多问题，这些多艰巨的挑战， 这些和服务本身有关系吗？⽐如写⼀个⽤户服务，对⽤户做 CRUD 操作，和刚才说的这些东⻄有⼀⽑钱 关系吗？发现有个地⽅不对，这些和服务本身没关系，⽽是服务间的通讯，这才是我们需要解决的问 题。 然后看⼀下我们的⽬标是什么。我们前⾯所有的努⼒，其实都是为了保证将客户端发出的业务请求，发 去⼀个正确的地⽅。什么是正确的地⽅？⽐如说有版本上的差异，应该去 2.0 版本，还是去 1.0 版本，需 要⽤什么样的负载均衡，要不要做灰度。最终这些考虑，都是让请求去⼀个你需要的正确的地⽅。 第三个，事情的本质。整个过程当中，这个请求是从来不发⽣更改的。⽐如我们前⾯说的⽤户服务，对 ⽤户做 CRUD，不管请求怎么⾛，业务语义不会发⽣变化。这是事情的本质，是不发⽣变化的东⻄。 这个问题具有⼀个⾼度的普适性：所有的语⾔，所有的框架，所有的组织，这些问题对于任何⼀个微服 务都是相同的。

讲到这⾥，⼤家应该有感觉了：这个问题是不是和哪个问题特别像？

![image 17](assets/imageFile17.png)

五⼗年前的前辈们，他们要解决的问题是什么？为什么会出现 TCP，TCP 解决了什么问题？⼜是怎么解决 的？ TCP 解决的问题和这个很像，都是要将请求发去⼀个正确的地⽅。所有的⽹络通讯，只要⽤到 TCP 协议，这 四个点都是⼀致的。 有了 TCP 之后会发⽣什么? 我们有了 TCP 之后，我们基于 TCP 来开发我们的应⽤，我们的应⽤需要做什么 事情? 我们的应⽤需要关⼼ TCP 层下链路层的实现吗？不需要。同理，我们基于 HTP 开发应⽤时，应⽤需 要关⼼ TCP 层吗？

![image 18](assets/imageFile18.png)

为什么我们开发微服务应⽤的时候就要这么关⼼服务的通讯层？我们把服务通讯层所有的事情学⼀遍，做⼀ 遍，我们做这么多是为什么？

![image 19](assets/imageFile19.png)

这种情况下，⾃然产⽣了另外⼀个想法：既然我们可以把⽹络访问的技术栈向下移为 TCP，我们是可以也有 类似的，把微服务的技术栈向下移？ 最理想的状态，就是我们在⽹络协议层中，增加⼀个微服务层来完成这个事情。但是因为标准问题，所以现 在没有实现，暂时这个东⻄应该不太现实，当然也许未来可能出现微服务的⽹络层。 之前有⼀些先驱者，尝试过使⽤代理的⽅案，常⻅的 nginx，haproxy，apache 等代理。这些代码和微服务 关系不⼤，但是提供了⼀个思路：在服务器端和客户端之间插⼊了⼀个东⻄完成功能，避免两者直接通讯。 当然代理的功能⾮常简陋，开发者⼀看，想法不错，但是功能不够，怎么办？

![image 20](assets/imageFile20.png)

这种情况下，第⼀代的 Sidecar 出现了，Sidecar 扮演的⻆⾊和代理很像，但是功能就⻬全很多，基本上原来 微服务框架在客户端实现的功能都会对应实现。 第⼀代的 sidecar 主要是列出来的这⼏家公司，其中最有名⽓的还是 netflix。

在这个地⽅我们额外提⼀下，注意第四个，前⾯三个功能都是国外的公司，但是其实 sidecar 这个东⻄并不 是只有国外的⼈在玩，国内也有⼚商和公司在做类似的事情。⽐如唯品会，我当年在唯品会基础架构部⼯作 的时候，在 2015 年上半年，我们的 OSP 服务化框架做了⼀个重⼤架构调整，加⼊了⼀个名为 local proxy 的 Sidecar。注意这个时间是 2015 上半年，和国外差不多。相信国内肯定还有类似的产品存在，只是不为外界 所知。

3为何选择Service Mesh？

![image 30](assets/imageFile30.png)

前⾯三个痛点都被解决了，有了 Service Mesh 之后这些问题都不是问题了。升级的痛点怎么解决？Service Mesh 是⼀个独⽴进程，可单独升级，⽽应⽤程序不⽤改。

![image 31](assets/imageFile31.png)

service mesh 是以远程调⽤的⽅式让客户端接⼊，只要能发出请求，简单发给 servicemesh 就可以。客户端 极度简化，对于典型的 rest 请求，⼏乎所有的语⾔都有完善的⽀持。⽽服务器端只要做⼀个事情，服务注 册。这样对于多语⾔的⽀持，就变得⾮常舒服了。现在终于可以真正的⾃由选择编程语⾔。

![image 32](assets/imageFile32.png)

这⾥有⼀个奇迹，⻥与熊掌兼得：同时实现降低⻔槛，功能增加。有些信奉质量守恒的同学会感觉不科学， 注意能同时实现这两个改进的原因，是把⼯作量最⼤最⾟苦的事情都交给了 Service Mesh。⽽ Service Mesh 是通⽤的，可以反复重⽤的。

![image 33](assets/imageFile33.png)

Service mesh 为业务开发团队带来的变⾰：降低⼊⻔⻔槛，提供稳定基座，帮助团队实现技术转型。最终达 到的⽬的是，让业务开发团队从微服务实现的具体技术细节中解放出来，回归业务。

![image 34](assets/imageFile34.png)

第⼆个变⾰，是对运维管理团队的强化，这⾥如果有做运维的同学，你们可以认真思考⼀下：如果有了 service mesh，你们对系统的管理和控制⼒会有多⼤的？注意很多功能的实现已经不再和应⽤有关，都在移 到 service mesh 中，⽽ service mesh 通常是在运维的掌控中。

![image 35](assets/imageFile35.png)

service mesh 对于新兴⼩众语⾔是极⼤的利好。对于新的语⾔来说，在和传统的主流编程语⾔竞争时，最痛 苦的事情是什么？是⽣态，⽐如各种类库，各种框架。在微服务这个领域，新兴⼩众语⾔想和 Java 等⽐拼， ⾮常的难：这是⽤⾃⼰的劣势对上别⼈的优势。⽽有了 Service Mesh 之后，⼩众语⾔就有机会避开这个弊 端，再不⽤和 Java ⽐拼⽣态，⽽是充分发挥⾃⼰的语⾔特点，做⾃⼰最擅⻓的领域。
