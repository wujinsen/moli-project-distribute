# 分布式理论基础

理解微服务（Nacos、Dubbo、Redis Session、秒杀 MQ）的取舍，需要 **CAP / BASE / 最终一致性** 框架。

## 1. CAP 定理

分布式系统三指标：

| 字母 | 含义 |
|------|------|
| **C** Consistency | 读到的都是最新写入 |
| **A** Availability | 每个请求都能得到响应 |
| **P** Partition tolerance | 网络分区时系统仍可运行 |

**定理**：三者最多同时满足两个。实践中 **P 必须接受**（跨机房/跨 AZ 网络会断），故常在 **C 与 A 之间权衡**。

| 选型 | 例子 |
|------|------|
| CP | 强一致注册中心选主、Zookeeper |
| AP | 高可用缓存、CDN 多副本（短暂不一致可接受） |

：**Nacos 注册**偏 AP 可用；**MySQL 单库**偏 CP；**Redis Session** 复制延迟下可能短暂会话不一致 → 见 [[security/认证与会话机制]] 故障排查。

## 2. BASE 理论

- **BA** Basically Available：基本可用（降级、限流 [[middleware/sentinel-限流与熔断]]）
- **S** Soft state：软状态，允许中间态
- **E** Eventually consistent：最终一致

互联网业务多数接受**最终一致**，用 [[middleware/消息队列]]、对账、补偿代替跨库强一致两阶段提交。

## 4. 分布式事务（了解）

Seata、RocketMQ 事务消息等用于强一致跨库；当前常见以 **单库 + 消息最终一致** 为主，未全面引入 Seata。
