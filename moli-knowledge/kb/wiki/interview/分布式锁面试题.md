# 分布式锁（面试题系列）

> 概念全貌见枢纽页 [[分布式锁]]；Redis 演进细节见 [[redis分布式锁实现]]。

## Q1. 为什么不能用 synchronized/Lock？分布式锁解决什么？

`synchronized`/`Lock` 只在**单个 JVM 进程内**有效。分布式多进程下，需要一个外部中间人（DB/Redis/ZK）协调，保证同一时刻只有一个进程的线程能操作共享资源。

## Q2. 一个合格的分布式锁要满足哪些条件？

互斥、防死锁（超时）、可重入、高可用/容错、高性能、**只有持有者能释放**。

## Q3. 有哪几种实现？怎么排序选型？

数据库 / Redis（缓存）/ ZooKeeper。

- 性能：**Redis > ZK > 数据库**
- 可靠性：**ZK > Redis > 数据库**
- 理解难度：数据库 < Redis < ZK

详见 [[分布式锁]] 对比表。

## Q4. Redis 怎么加锁？为什么不能 SETNX + EXPIRE 两条命令？

正确姿势：**`SET key 唯一value NX PX 30000`**（一条命令原子地「不存在才设置 + 带过期」）。

- `SETNX` 再 `EXPIRE` 是两条命令、**非原子**：若设置完锁就宕机，过期没设上 → 死锁。
- Redis 2.6.12 起 `SET ... NX PX` 合并为原子操作，解决此问题。

## Q5. 锁误删问题？怎么解决？

场景：客户端 1 加锁后执行过久（GC/网络），锁**超时自动释放**；客户端 2 拿到锁；客户端 1 执行完 `DEL` 把**客户端 2 的锁**删了。

解决：

1. value 存**唯一标识**（如 UUID/snowflake），释放前先比对是不是自己的锁。
2. 「比对 + 删除」也要原子，用 **Lua 脚本**：

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
 return redis.call("del", KEYS[1])
else
 return 0
end
```

## Q6. 锁过期了但业务没执行完怎么办？（续期/看门狗）

开一个**守护线程（看门狗）**定时检测，快过期且业务没完成就自动续期。**Redisson** 内置该机制（默认 30s，每 1/3 时间续一次）。

## Q7. 可重入锁怎么实现？

用 **Redis Hash**：field=线程唯一标识，value=重入次数。加锁时 `hincrby +1`、解锁 `-1`，减到 0 才 `del`。全程用 Lua 保证原子。Redisson 即如此实现。

## Q8. 主从架构会有什么问题？Redlock 是什么？

- **主从异步复制**：客户端在 master 加锁后，未同步到 slave 时 master 宕机，slave 升主 → 锁丢失，另一个客户端又能加锁。
- **Redlock（红锁）**：Redis 作者提出，部署 N 个（奇数，建议 5）独立实例；客户端依次向各实例加锁，**多数（N/2+1）成功且总耗时 < 锁有效期**才算成功，否则向所有实例解锁。
- **争议**：Martin Kleppmann 质疑它依赖时钟一致性、GC 停顿仍可能失效，主张用 **fencing token**（每次操作带递增令牌校验）。antirez 有反驳。结论：没有绝对安全的锁，正确性场景要**业务幂等兜底**。

## Q9. 数据库实现的要点与坑？

- **唯一索引插入**：`insert` 成功＝加锁，`delete`＝释放。坑：强依赖 DB、无超时、非阻塞、非重入。
- **`for update` 行锁**：查不到则插，靠 `connection.commit()` 释放；宕机自动释放。坑：`method_name` **必须唯一索引**，否则 InnoDB 退化**表锁**；长事务占连接，可能撑爆连接池。

## Q10. ZooKeeper 怎么实现？

每个客户端在锁节点下建**临时顺序节点**，序号最小者持锁；其余监听**前驱节点**。释放＝删节点；客户端掉线 session 断 → 临时节点自动删，天然防死锁。常用 Curator 的 `InterProcessMutex`。坑：性能略低（创建/删除走 Leader），网络抖动误删（靠重试策略缓解）。
