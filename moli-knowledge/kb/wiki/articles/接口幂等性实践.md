# 接口幂等性实践

**幂等**：同一业务请求执行多次，效果与执行一次相同。微服务超时重试、用户双击、MQ 重复消费都会破坏幂等。

## 1. 设计原则

1. **业务唯一键**：订单号、秒杀 `(activityId, userId)` 等。
2. **状态机**：已支付/已关闭不可再次支付。
3. **先查后写**：处理前查是否已成功。

## 2. 常见实现

| 方案 | 适用 | 茉莉触点 |
|------|------|----------|
| **Token 防重** | 表单提交 | Redis 存 token，Lua 原子 get+del |
| **数据库唯一约束** | 订单号、业务单号 | MySQL UNIQUE |
| **乐观锁 version** | 库存扣减 | `UPDATE ... WHERE version=?` |
| **悲观锁** | 低并发强一致 | `SELECT ... FOR UPDATE` |
| **分布式锁** | 跨节点互斥 | [[redis分布式锁实现]] |
| **去重表/防重表** | 与业务同事务 | insert 唯一键失败即重复 |
| **Redis Set** | 请求指纹 MD5 | 短时去重 |

### Token 流程（摘要）

1. 进入页面前 `GET /token` → Redis 写入。
2. 提交时带 token；服务端 Lua：`if get==token then del else reject`。
3. **先删 token 再执行业务**时需保证原子性（Lua/锁），否则失败难重试。

## 3. 秒杀与订单

- 秒杀 Lua 已保证**库存 + 一人一单**原子性 [[秒杀设计]]。
- 订单 MQ 消费应**幂等插入**（唯一键或状态检查）。
- Dubbo **重试**默认可能重复调用 Provider → 写操作需幂等。

## 4. REST 语义

GET/PUT/DELETE 应幂等；POST 创建资源通常不幂等，需显式防重。
