# 认证与会话机制

的跨服务登录态机制。核心结论：**不用 JWT，token 就是 Shiro 的 Session ID，存共享 Redis。**

## 关键设计

| 点 | 说明 |
|----|------|
| token 形态 | `login_token_{uuid}`，即 Shiro Session ID（不是 JWT） |
| 传递方式 | 请求头 `Authorization: login_token_xxx`（**不用 Cookie**） |
| 存储 | Redis，key `shiro:session:login_token_*`；授权缓存 `shiro:cache:*` |
| 密码 | SHA-256 × 15 轮 + 固定盐 `moli`（`SHA256Util`） |
| 会话有效期 | 默认 86400s |
| 单/多端登录 | `shiro.single-session` 控制；索引 key `moli:shiro:user-session(s):{userName}` |

## 登录流程（user-center）

```
前端 POST /UserCenter/login {userName,password}
 → 网关 StripPrefix → POST /login
 → ShiroRealm.doGetAuthenticationInfo 查 sys_user（status=0 → 锁定）
 → HashedCredentialsMatcher 校验（SHA-256×15）
 → 成功：token=SessionId；写 sys_login_log
 → 返回 LoginVo { token, user, menuVoList, permissions, systemList }
```

## 跨服务校验（关键）

**只有 能 `login()`**；// 通过 `moli-user-center-shiro-starter`：

1. 从**共享 Redis** 读同一个 `shiro:session:login_token_*` 拿到 `SysUser` Principal；
2. 通过 **Dubbo** 调 user-center `getUserById` 校验账号有效（停用即时失效）；
3. 命中 `@RequiresPermissions` 时再 Dubbo `getPermissionsByUserId` 拉权限。

业务服务的 `ShiroRealm.doGetAuthenticationInfo` **直接抛异常**，从机制上禁止本地登录。

> ⚠️ 因此所有业务服务**必须连同一个 Redis（含相同 database）**，否则读不到会话。

## 过滤器链要点

`/login`、`/swagger-*`、`/actuator/**`、`/sso/validate`、`/loadtest/**` 为 `anon`；其余 `/**` 走 `authc`（自定义 `AuthenticationFilter`，未登录返回 JSON 错误码而非重定向）。

## JWT 与 Session（raw javaweb/jwt）

| | Session | JWT |
|---|---------|-----|
| 状态 | 服务端存 | 自包含，无服务端会话 |
| 扩展 | 需 sticky/共享存储 | 适合跨域 API |
| 撤销 | 删 session | 短 TTL + 黑名单 |

Cookie 存 token 时注意 `HttpOnly`、`Secure`、CSRF 防护。见 [[security/api-接口安全设计]]。
