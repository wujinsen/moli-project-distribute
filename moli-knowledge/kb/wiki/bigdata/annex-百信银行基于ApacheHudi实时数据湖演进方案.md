# ⼀、背景

百信银⾏，全称为 “中信百信银⾏股份有限公司”，是⾸家获批独⽴法⼈形式的直销银⾏。作为⾸家国 有控股的互联⽹银⾏，相⽐于传统⾦融⾏业，百信银⾏对数据敏捷性有更⾼的要求。 数据敏捷，不仅要求数据的准确性，还要求数据到达的实时性，和数据传输的安全性。为了满⾜我⾏ 数据敏捷性的需求，百信银⾏⼤数据部承担起了建设实时计算平台的职责，保证了数据快速，安全且 标准得在线送达。 受益于⼤数据技术的发展和更新迭代，⽬前⼴为⼈知的批流⼀体的两⼤⽀柱分别是：“统⼀计算引擎” 与 “统⼀存储引擎”。

Flink，作为⼤数据实时计算领域的佼佼者，1.12 版本的发布让它进⼀步提升了统⼀计算引擎的能 ⼒；

同时随着数据湖技术 Hudi 的发展，统⼀存储引擎也迎来了新⼀代技术变⾰。

在 Flink 和 Hudi 社区发展的基础上，百信银⾏构建了实时计算平台，同时将实时数据湖 Hudi 集成到 实时计算平台之上。结合⾏内数据治理的思路，实现了数据实时在线、安全可靠、标准统⼀，且有敏 捷数据湖的⽬标。

数据具有⼆义性：两套计算逻辑，实时数据和批量数据经常对不上，准确性难以分辨；

重⽤ Kafka 消息队列：Kafka 保留往往按照天或者⽉保留，不能全量保留数据，⽆法使⽤现有的 adhoc 查询引擎分析。

Update / Delete 记录：Hudi 使⽤细粒度的⽂件/记录级别索引，来⽀持 Update / Delete 记录，同 时还提供写操作的事务保证，⽀持 ACID 语义。查询会处理最后⼀个提交的快照，并基于此输出结 果；

变更流：Hudi 对获取数据变更提供了流的⽀持，可以从给定的时间点获取给定表中已 updated / inserted / deleted 的所有记录的增量流，可以查询不同时间的状态数据；

技术栈统⼀：可以兼容我们现有的 adhoc 查询引擎 presto，spark。

社区更新迭代速度快：已经⽀持 Flink 两种不同⽅式的的读写操作，如 COW 和 MOR。

![image 5](assets/imageFile5.png)

⾸先，我们可以看到，对于新的表的⼊仓逻辑，我们通过实时计算平台使⽤ Flink 写⼊到 datalake 中（新的贴源层，Hudi 格式存储），数据分析师和数据科学家，可以直接使⽤ datalake 层的数据 进⾏数据分析和机器学习建模。如果数据仓库的模型需要使⽤ datalake 的数据源，需要⼀层转换 ODS 的逻辑，这⾥的转换逻辑分为两种情况：

第⼀种，对于增量模型，⽤户只需要将最新 datalake 的分区使⽤快照查询放到 ODS 中即可。 第⼆种，对于全量模型，⽤户需要把 ODS 前⼀天的快照和 datalake 最新的快照查询的结果进 ⾏⼀次合并，形成最新的快照再放到 ODS 当前的分区中，以此类推。

我们这么做的原因是，对于现有的数仓模型不⽤改造，只是把 ODS 的数据来源换成 datalake，时效性 强。同时满⾜了数据分析和数据科学家准实时获取数据的诉求。

另外，对于原始的 ODS 存在的数据，我们开发了将 ODS 层的数据进⾏了⼀次初始化⼊ datalake 的脚本。

如果 ODS 层数据每天是全量的快照，我们只将最新的⼀次快照数据初始化到 datalake 的相同 分区，然后实时⼊ datalake 的链路接⼊；

如果 ODS 层的数据是增量的，我们暂时不做初始化，只在 datalake 中重新建⼀个实时⼊湖的 链路，然后每天做⼀次增量⽇切到 ODS 中。

最后，如果是⼀次性⼊湖的数据，我们使⽤批量⼊湖的⼯具导⼊到 datalake 中即可。

## 3. 技术挑战

在我们调研的初期，Hudi 对 Flink 的⽀持不是很成熟，我们对 Spark - StrunctStreaming 做了⼤量 的开发和测试。从我们 PoC 测试结果上看，

如果使⽤⽆分区的 COW 写⼊的⽅式，在千万级写⼊量的时候会发现写⼊越来越慢；

后来我们将⽆分区的改为增量分区的⽅式写⼊，速度提升了很多。

之所以会产⽣这个问题，是因为 spark 在写⼊时会读取 basefile ⽂件索引，⽂件越⼤越多，读取⽂件 索引就会越慢，因此会产⽣写⼊越来越慢的情况。

同时，随着 Flink 对 hudi ⽀持越来越好，我们的⽬标是打算将 Hudi ⼊湖的功能集成到实时计算平 台。因此，我们把实时计算平台对 Hudi 做了集成和测试，期间也遇到⼀些问题，典型的问题有：

类冲突

不能找到 clas ⽂件

rocksdb 冲突。

为了解决这些不兼容的问题，我们将对 Hudi 的依赖，重新构造了⼀个独⽴的模块，这个⼯程只是把 Hudi 的依赖打包成⼀个 shade package。

当有依赖冲突时，我们会把 Flink 模块相关或者 Hudi 模块相关的冲突依赖 exclude 掉。

⽽如果有其他依赖包找不到的情况，我们会把相关的依赖通过 pom ⽂件引⼊进来。

在使⽤ Hudi on Flink 的⽅案中，也遇到了相关的问题，⽐如，checkpoint 太⼤导致 checkpoint 时 间过⻓⽽引起的失败。这个问题，我们设置状态的 TL 时间，把全量 checkpoint 改为增量 checkpoint，且提⾼并⾏度来解决。

COW 和 MOR 的选择。⽬前我们使⽤的 Hudi 表以 COW 居多，之所以选择 COW，

第⼀是因为我们⽬前历史存量 ODS 的数据都是⼀次性导⼊到 datalake 数据表中，不存在写放 ⼤的情况。

另外⼀个原因是，COW 的⼯作流⽐较简单，不会涉及到 compaction 这样的额外操作。

如果是新增的 datalake 数据，并且存在⼤量的 update，并且实时性要求较⾼的情况下，我们更多的选 择 MOR 格式来写，尤其写 QPS ⽐较⼤的情况下，我们会采⽤异步 compaction 的操作，避免写放 ⼤。除了这种情况外，我们还是会更倾向以 COW 的格式来写。

# 四、百信银⾏实时数据湖的未来

在我⾏实时数据湖的架构中，我们的⽬标是将实时数仓的整个链路构建在Hudi之上，架构体系如图：

![image 7](assets/imageFile7.png)

我们整体的⽬标规划是替代 kafka，把 Hudi 作为中间存储，将数仓建设在 Hudi 之上，并以 Flink 作为 流批⼀体计算引擎。这样做的好处有：

MQ 不再担任实时数据仓库存储的中间存储介质，⽽ Hudi 存储在 HDFS 上，可以存储海量数据 集；

实时数据仓库中间层可以使⽤ OLAP 分析引擎查询中间结果数据；

真正意义上的批流⼀体，数据 T+1 延迟的问题得到解决；

读时 Schema 不再需要严格定义 Schema 类型，⽀持 schema evolution；

⽀持主键索引，数据查询效率数倍增加，并且⽀持 ACID 语义，保证数据不重复不丢失；

Hudi 具有 Timeline 的功能，可以更多存储数据中间的状态数据，数据完备性更强。
