## 什么是幻读?

在说幻读之前，我们要先来了解脏读和不可重复读。

### 脏读

当⼀个事务读取到另外⼀个事务修改但未提交的数据时，就可能发⽣脏读。

![image 3](assets/imageFile3.png)

在我们的例⼦中，事务2修改了⼀⾏，但是没有提交，事务1读了这个没有提交的数据。

现在如果事务2回滚了刚才的修改或者做了另外的修改的话，事务1中查到的数据就是不正确的了，所以这条 数据就是脏读。

### 不可重复读

“不可重复读”现象发⽣在当执⾏SELECT 操作时没有获得读锁或者SELECT操作执⾏完后⻢上释放了读锁；另 外⼀个事务对数据进⾏了更新，读到了不同的结果。

![image 4](assets/imageFile4.png)

在这个例⼦中，事务2提交成功，因此他对id为1的⾏的修改就对其他事务可⻅了。导致了事务1在此前读的 age=1，第⼆次读的age=2，两次结果不⼀致,这就是不可重复读。

### 幻读

“幻读”⼜叫"幻象读",是 '不可重复读 '的⼀种特殊场景：当事务1两次执⾏ 'SELECT . WHERE'检索⼀定范围 内数据的操作中间，事务2在这个表中创建了(如 [INSERT])了⼀⾏新数据，这条新数据正好满⾜事务1的 “WHERE”⼦句。

![image 5](assets/imageFile5.png)

如图事务1执⾏了两遍同样的查询语句，第⼆遍⽐第⼀遍多出了⼀条数据，这就是幻读。

### 三者到底什么区别

三者的场景介绍完,但是⼀定仍然有很多同学搞不清楚,它们到底有什么区别，我总结⼀下。

脏读：指读到了其他事务未提交的数据。 不可重复读：读到了其他事务已提交的数据(update)。 不可重复读与幻读都是读到其他事务已提交的数据,但是它们针对点不同。 不可重复读：update。 幻读：delete，insert。

## MySQL中的四种事务隔离级别

未提交读

未提交读（READ UNCOMI TED）是最低的隔离级别，在这种隔离级别下，如果⼀个事务已经开始写数 据，则另外⼀个事务则不允许同时进⾏写操作，但允许其他事务读此⾏数据。

把脏读的图拿来分析分析，因为事务2更新id=1的数据后，仍然允许事务1读取该条数据,所以事务1第⼆次执⾏ 查询，读到了事务2更新的结果，产⽣了脏读。

![image 6](assets/imageFile6.png)

### 已提交读

由于MySQL的I noDB默认是使⽤的 R级别，所以我们先要将该sesion开启成RC级别，并且设置binlog的模 式

SET session transaction isolation level read committed;SET SESSION binlog_format = 'ROW'; （或者是MIXED）

在已提交读（READ COMI TED）级别中，读取数据的事务允许其他事务继续访问该⾏数据，但是未提交的 写事务将会禁⽌其他事务访问该⾏，会对该写锁⼀直保持直到到事务提交。

同样，我们来分析脏读，事务2更新id=1的数据后，在提交前，会对该对象写锁，所以事务1读取id=1的数据 时，会⼀直等待事务2结束，处于阻塞状态，避免了产⽣脏读。

![image 7](assets/imageFile7.png)

同样，来分析不可重复读，事务1读取id=1的数据后并没有锁住该数据，所以事务2能对这条数据进⾏更新， 事务2对更新并提交后，该数据⽴即⽣效，所以事务1再次执⾏同样的查询，查询到的结果便与第⼀次查到的 不同，所以已提交读防不了不可重复读。

![image 8](assets/imageFile8.png)

### 可重复读

在可重复读（REPEATABLE READS）是介于已提交读和可串⾏化之间的⼀种隔离级别(废话😅 )，它是I noDb 的默认隔离级别，它是我这篇⽂章的重点讨论对象，所以在这⾥我先卖个关⼦,后⾯我会详细介绍。

### 可串⾏化

可串⾏化（Serializable ）是⾼的隔离级别，它求在选定对象上的读锁和写锁保持直到事务结束后才能释放， 所以能防住上诉所有问题，但因为是串⾏化的，所以效率较低。

![image 9](assets/imageFile9.png)

到此为⽌，相信⼤家已经知道答案了，这是怎么做到的呢?

### 悲观锁与乐观锁

我们前⾯说的在对象上加锁，是⼀种悲观锁机制。

有很多⽂章说可重复读的隔离级别防不了幻读，是认为可重复读会对读的⾏加锁，导致他事务修改不了这条 数据，直到事务结束。

但是这种⽅案只能锁住数据⾏，如果有新的数据进来，是阻⽌不了的，所以会产⽣幻读。

可是MySQL、ORACLE、PostgreSQL等已经是⾮常成熟的数据库了，怎么会单纯地采⽤这种如此影响性能的 ⽅案呢?

![image 11](assets/imageFile11.png)

我来介绍⼀下悲观锁和乐观锁。

悲观锁 正如其名，它指的是对数据被外界（包括本系统当前的其他事务，以及来⾃外部系统的事务处理）修改持保 守态度，因此，在整个数据处理过程中，将数据处于锁定状态。

读取数据时给加锁，其它事务⽆法修改这些数据。修改删除数据时也要加锁，其它事务⽆法读取这些数据。

乐观锁 相对悲观锁⽽⾔，乐观锁机制采取了更加宽松的加锁机制。悲观锁⼤多数情况下依靠数据库的锁机制实现， 以保证操作最⼤程度的独占性。

但随之⽽来的就是数据库性能的⼤量开销，特别是对⻓事务⽽⾔，这样的开销往往⽆法承受。

⽽乐观锁机制在⼀定程度上解决了这个问题。乐观锁，⼤多是基于数据版本（ Version ）记录机制实现。

何谓数据版本？即为数据增加⼀个版本标识，在基于数据库表的版本解决⽅案中，⼀般是通过为数据库表增 加⼀个 “version” 字段来实现。读取出数据时，将此版本号⼀同读出，之后更新时，对此版本号加⼀。

此时，将提交数据的版本数据与数据库表对应记录的当前版本信息进⾏⽐对，如果提交的数据版本号⼤于数 据库表当前版本号，则予以更新，否则认为是过期数据。

MySQL、ORACLE、PostgreSQL等都是使⽤了以乐观锁为理论基础的MVC（多版本并发控制）来避免不可 重复读和幻读,MVC的实现没有固定的规范，每个数据库都会有不同的实现⽅式，这⾥讨论的是I noDB的 MVC。

### MVC(多版本并发控制)

在I noDB中，会在每⾏数据后添加两个额外的隐藏的值来实现MVC，这两个值⼀个记录这⾏数据何时被创 建，另外⼀个记录这⾏数据何时过期（或者被删除）。

在实际操作中，存储的并不是时间，⽽是事务的版本号，每开启⼀个新事务，事务的版本号就会递增。在可 重读Repeatable reads事务隔离级别下：

SELECT时，读取创建版本号<=当前事务版本号，删除版本号为空或>当前事务版本号。

INSERT时，保存当前事务版本号为⾏的创建版本号 DELETE时，保存当前事务版本号为⾏的删除版本号 UPDATE时，插⼊⼀条新纪录，保存当前事务版本号为⾏创建版本号，同时保存当前事务版本号到原来删 除的⾏

![image 12](assets/imageFile12.png)

通过MVC，虽然每⾏记录都要额外的存储空间来记录version，需要更多的⾏检查⼯作以及⼀些额外的维护 ⼯作，但可以减少锁的使⽤，⼤多读操作都不⽤加锁，读取数据操作简单，性能好。

细⼼的同学应该也看到了，通过MVC读取出来的数据其实是历史数据，⽽不是最新数据。

这在⼀些对于数据时效特别敏感的业务中，很可能出问题，这也是MVC的短板之处，有办法解决吗？当然 有。

MCV这种读取历史数据的⽅式称为快照读(snapshot read)，⽽读取数据库当前版本数据的⽅式，叫当前读 (curent read)。

快照读 我们平时只⽤使⽤select就是快照读，这样可以减少加锁所带来的开销。

select * from table ....

当前读

对于会对数据修改的操作(update、insert、delete)都是采⽤当前读的模式。在执⾏这⼏个操作时会读取最新 的记录，即使是别的事务提交的数据也可以查询到。

假设要update⼀条记录，但是在另⼀个事务中已经delete掉这条数据并且comit了，如果update就会产⽣冲 突，所以在update的时候需要知道最新的数据。读取的是最新的数据，需要加锁。

以下第⼀个语句需要加共享锁，其它都需要加排它锁。

select * from table where ? lock in share mode; select * from table where ? for update; inse rt; update; delete;

我们再利⽤当前读来做试验。

![image 13](assets/imageFile13.png)

可以看到在读提交的隔离级别中，事务1修改了所有clas_id=1的数据，当时当事务2 insert后，事务A莫名奇 妙地多了⼀⾏clas_id=1的数据，⽽且没有被之前的update所修改，产⽣了读提交下的的幻读。

⽽在可重复度的隔离级别下，情况就完全不同了。

事务1在update后，对该数据加锁，事务B⽆法插⼊新的数据，这样事务A在update前后数据保持⼀致，避免 了幻读，可以明确的是，update锁的肯定不只是已查询到的⼏条数据，因为这样⽆法阻⽌insert，有同学会 说，那就是锁住了整张表呗。

还是那句话，Mysql已经是个成熟的数据库了，怎么会采⽤如此低效的⽅法呢？其实这⾥的锁，是通过nextkey锁实现的。

### Next-Key锁

在Users这张表⾥⾯，clas_id是个⾮聚簇索引，数据库会通过B+树维护⼀个⾮聚簇索引与主键的关系，简单 来说，我们先通过clas_id=1找到这个索引所对应所有节点，这些节点存储着对应数据的主键信息，即id=1， 我们再通过主键id=1找到我们要的数据，这个过程称为回表。

假设我们上⾯⽤到的User表需要对Name建⽴⾮聚簇索引，是怎么实现的呢？我们看下图：

![image 14](assets/imageFile14.png)

B+树的特点是所有数据都存储在叶⼦节点上，以⾮聚簇索引的秦寿⽣为例，在秦寿⽣的右叶⼦节点存储着所 有秦寿⽣对应的Id，即图中的34。

在我们对这条数据做了当前读后，就会对这条数据加⾏锁，对于⾏锁很好理解，能够防⽌其他事务对其进⾏ update或delete，但为什么要加GAP锁呢?

还是那句话，B+树的所有数据存储在叶⼦节点上，当有⼀个新的叫秦寿⽣的数据进来，⼀定是排在在这条 id=34的数据前⾯或者后⾯的，我们如果对前后这个范围进⾏加锁了，那当然新的秦寿⽣就插不进来了。

那如果有⼀个新的范统要插进⾏呢？因为范统的前后并没有被锁住，是能成功插⼊的，这样就极⼤地提⾼了 数据库的并发能⼒。

## ⻢失前蹄

上⽂中说了可重复读能防不可重复读，还能防幻读，它能防住所有的幻读吗？当然不是，也有⻢失前蹄的时 候。

⽐如如下的例⼦:

![image 15](assets/imageFile15.png)

- 1. a事务先select，b事务insert确实会加⼀个gap锁，但是如果b事务comit，这个gap锁就会释放（释放后a 事务可以随意操作）
- 2. a事务再select出来的结果在MVC下还和第⼀次select⼀样
- 3. 接着a事务不加条件地update，这个update会作⽤在所有⾏上（包括b事务新加的）
- 4. a事务再次select就会出现b事务中的新⾏，并且这个新⾏已经被update修改了。


Mysql官⽅给出的幻读解释是：只要在⼀个事务中，第⼆次select多出了row就算幻读，所以这个场景下，算 出现幻读了。
