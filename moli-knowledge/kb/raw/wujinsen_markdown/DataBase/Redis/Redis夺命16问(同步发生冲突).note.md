# 5.redis 的持久化机制有哪些？优缺点说说

redis 有两种持久化的⽅式，AOF 和 RDB.

![image 5](<Redis夺命16问(同步发生冲突).note_images/imageFile5.png>)

## AOF:

redis 每次执⾏⼀个命令时,都会把这个「命令原本的语句记录到⼀个.aod的⽂件当中,然后通过fsync策略,将 命令执⾏后的数据持久化到磁盘中」(不包括读命令)，

AOF的优缺点

![image 6](<Redis夺命16问(同步发生冲突).note_images/imageFile6.png>)

AOF 的「优点」:

- 1.AOF可以「更好的保护数据不丢失」，⼀般AOF会以每隔1秒，通过后台的⼀个线程去执⾏⼀次fsync 操作，如果redis进程挂掉，最多丢失1秒的数据

- 2.AOF是将命令直接追加在⽂件末尾的,「写⼊性能⾮常⾼」

- 3.AOF⽇志⽂件的命令通过⾮常可读的⽅式进⾏记录，这个⾮常「适合做灾难性的误删除紧急恢 复」，如果某⼈不⼩⼼⽤ flushall 命令清空了所有数据，只要这个时候还没有执⾏ rewrite，那么就可以 将⽇志⽂件中的 flushall 删除，进⾏恢复


![image 7](<Redis夺命16问(同步发生冲突).note_images/imageFile7.png>)

AOF 的「缺点」:

- 1.对于同⼀份数据源来说,⼀般情况下AOF ⽂件⽐ RDB 数据快照要⼤

- 2.由于 .aof 的每次命令都会写⼊,那么相对于 RDB 来说「需要消耗的性能也就更多」，当然也会有 aof 重写将 aof ⽂件优化。

- 3.「数据恢复⽐较慢」，不适合做冷备。


## RDB:

把某个时间点 redis 内存中的数据以⼆进制的形式存储的⼀个.rdb为后缀的⽂件当中,也就是「周期性的备份 redis中的整个数据」,这是redis默认的持久化⽅式,也就是我们说的快照(snapshot)，是采⽤ fork ⼦进程的⽅ 式来写时同步的。

RDB的优缺点

![image 8](<Redis夺命16问(同步发生冲突).note_images/imageFile8.png>)

RDB的优点:

- 1.它是将某⼀时间点redis内的所有数据保存下来,所以当我们做「⼤型的数据恢复时,RDB的恢复 速度会很快」

- 2.由于RDB的FROK⼦进程这种机制,队友给客户端提供读写服务的影响会⾮常⼩


![image 9](<Redis夺命16问(同步发生冲突).note_images/imageFile9.png>)

RDB的缺点:

举个例⼦假设我们定时5分钟备份⼀次,在10:00的时候 redis 备份了数据,但是如果在10:04的时候服务挂 了,那么我们就会丢失在10:00到10:04的整个数据

- 1:「有可能会产⽣⻓时间的数据丢失」

- 2:可能会有⻓时间停顿:我们前⾯讲了,fork ⼦进程这个过程是和 redis 的数据量有很⼤关系的,如果「数 据量很⼤,那么很有可能会使redis暂停⼏秒」


# 6. Redis的过期键的删除策略有哪些？

过期策略通常有以下三种：

![image 10](<Redis夺命16问(同步发生冲突).note_images/imageFile10.png>)

定时过期：每个设置过期时间的key都需要创建⼀个定时器，到过期时间就会⽴即清除。该策略可以⽴即清 除过期的数据，对内存很友好；但是会占⽤⼤量的CPU资源去处理过期的数据，从⽽影响缓存的响应时间 和吞吐量。

惰性过期：只有当访问⼀个key时，才会判断该key是否已过期，过期则清除。该策略可以最⼤化地节省 CPU资源，却对内存⾮常不友好。极端情况可能出现⼤量的过期key没有再次被访问，从⽽不会被清除，占 ⽤⼤量内存。

定期过期：每隔⼀定的时间，会扫描⼀定数量的数据库的expires字典中⼀定数量的key，并清除其中已过 期的key。该策略是前两者的⼀个折中⽅案。通过调整定时扫描的时间间隔和每次扫描的限定耗时，可以在 不同情况下使得CPU和内存资源达到最优的平衡效果。

# 7. Redis的内存满了怎么办？

实际上Redis定义了「8种内存淘汰策略」⽤来处理redis内存满的情况：

- 1.noeviction：直接返回错误，不淘汰任何已经存在的redis键

- 2.allkeys-lru：所有的键使⽤lru算法进⾏淘汰

- 3.volatile-lru：有过期时间的使⽤lru算法进⾏淘汰

- 4.allkeys-random：随机删除redis键

- 5.volatile-random：随机删除有过期时间的redis键

- 6.volatile-ttl：删除快过期的redis键

- 7.volatile-lfu：根据lfu算法从有过期时间的键删除


8.allkeys-lfu：根据lfu算法从所有键删除

# 14.cluster的故障恢复是怎么做的？

判断故障的逻辑其实与哨兵模式有点类似，在集群中，每个节点都会定期的向其他节点发送ping命 令，通过有没有收到回复来判断其他节点是否已经下线。 如果⻓时间没有回复，那么发起ping命令的节点就会认为⽬标节点疑似下线，也可以和哨兵⼀样称作 主观下线，当然也需要集群中⼀定数量的节点都认为该节点下线才可以，我们来说说具体过程：

![image 17](<Redis夺命16问(同步发生冲突).note_images/imageFile17.png>)

- 1.当A节点发现⽬标节点疑似下线，就会向集群中的其他节点散播消息，其他节点就会向⽬标节点发送命 令，判断⽬标节点是否下线

- 2.如果集群中半数以上的节点都认为⽬标节点下线，就会对⽬标节点标记为下线，从⽽告诉其他节点，让 ⽬标节点在整个集群中都下线


# 15.主从同步原理是怎样的？

- 1.当⼀个从数据库启动时，它会向主数据库发送⼀个SYNC命令，master收到后，在后台保存快照， 也就是我们说的RDB持久化，当然保存快照是需要消耗时间的，并且redis是单线程的，在保存快照 期间redis受到的命令会缓存起来

- 2.快照完成后会将缓存的命令以及快照⼀起打包发给slave节点，从⽽保证主从数据库的⼀致性。

- 3.从数据库接受到快照以及缓存的命令后会将这部分数据写⼊到硬盘上的临时⽂件当中，写⼊完成 后会⽤这份⽂件去替换掉RDB快照⽂件，当然，这个操作是不会阻塞的，可以继续接收命令执⾏， 具体原因其实就是fork了⼀个⼦进程，⽤⼦进程去完成了这些功能。


因为不会阻塞，所以，这部分初始化完成后，当主数据库执⾏了改变数据的命令后，会异步的给 slave，这也就是我们说的复制同步阶段，这个阶段会贯穿在整个中从同步的过程中，直到主从同步结 束后，复制同步才会终⽌。

# 16.⽆硬盘复制是什么？

我们刚刚说了主从之间是通过RDB快照来交互的，虽然看来逻辑很简单，但是还是会存在⼀些问题， 但是会存在着⼀些问题。

- 1.master禁⽤了RDB快照时，发⽣了主从同步(复制初始化)操作，也会⽣成RDB快照，但是之后如果 master发成了重启，就会⽤RDB快照去恢复数据，这份数据可能已经很久了，中间就会丢失数据

- 2.在这种⼀主多从的结构中，master每次和slave同步数据都要进⾏⼀次快照，从⽽在硬盘中⽣成RDB ⽂件，会影响性能


为了解决这种问题，redis在后续的更新中也加⼊了⽆硬盘复制功能，也就是说直接通过⽹络发送给 slave，避免了和硬盘交互，但是也是有io消耗。
