⼀、概念

当微服务之间调⽤时服务A向服务B重复发送消息或者⽤户多次点击导致重复操作数据库。

例如⽀付订单接⼝，如果发⽣⽹络问题，导致客户端重复请求两次，就会导致扣款两次。 例如向数据库写⼊数据，重复请求会导致数据库中出现重复的脏数据。 幂等性就是说⼀个接⼝需要保证发⽣多次重复的请求，只有⼀次请求⽣效。

- ①对于每个请求需要有⼀个唯⼀的标识，如订单⽀付请求，需要包含订单的id，⼀个id最多⽀付⼀次
- ②处理完成后，需要有⼀个记录标识这个请求已经处理完成。


⼆、实现幂等性的思路

- 1.全局唯⼀id：需要根据实际业务⽣成,操作执⾏成功后⽣成这个id,每次执⾏操作前先判断这个id存不存 在,存在就是已执⾏,不存在则添加这个id.
- 2.去重表：就是利⽤数据库的唯⼀约束.如果重复新增某个唯⼀标识,就会报唯⼀约束异常,再利⽤事务回 滚.
- 3.利⽤版本号控制：多拥有更新操作.每次更新的时候需要在where条件中添加version判断,并更新 version.如果版本已更新就⽆法再次根据原版本号更新了.
- 4.在并发不⾼的系统,可以在新增或更新操作执⾏前先对关键数据进⾏查询,并根据实际业务设置判断,通 过后再执⾏操作 可以将以上操作编写为⾃定义注解，⽅便实现接⼝幂等性。


三、幂等解决⽅案

- 3.1 token机制（适⽤于下订单等操作）


流程

在执⾏业务前，获取token，服务器会把token保存到redis中； 然后调⽤业务接⼝请求时，把token携带过去，⼀般放在请求头； 服务器判断token是否存在redis中，存在表示第⼀次请求，然后删除token，继续执⾏业务； 如果判断token不存在redis中，就表示是重复操作，直接返回重复标记给client。保证了不会重复提 交。

危险性 先删除token还是后删除token：先删除可能导致业务执⾏失败后⽆法再次提交成功需要再次提交表 单，后删除可能导致业务处理成功但是没有删除token。采⽤先删除策略，但是需要保证redis操作的原 ⼦性。 解决措施：token获取、⽐较和删除必须是原⼦性的。可以使⽤分布式锁或在redis使⽤lua脚本完成。 if redis.cal('get',KEYS[1]) = ARGV[1] then return redis.cal('del',KEYS[1]) else return 0 end 将脚本提交到redis执⾏，保证原⼦性。

缺点 对代码的侵⼊性较强。

- 3.2 各种锁机制（适⽤于减库存等操作）

- 3.2.1 数据库悲观锁

select * from x where id = 1 for update; 悲观锁使⽤时⼀般伴随事务⼀起使⽤，数据锁定时间较⻓，根据需求选⽤。 另外需要注意的是，id字段⼀定是主键或者唯⼀索引，不然可能造成锁表的结果，处理起来会⾮常麻 烦。

- 3.2.2 数据库乐观锁

这种⽅法适合再更新场景中 update t_gods set count = count - 1,version = version + 1 where god_id = 2 and version = 1; 根据version版本，也就是在操作库存前先获取当前商品的version版本号，然后操作的时候带上此 version。 详解：我们第⼀次操作库存时，得到version为1，调⽤库存服务version变成了2,；但返回给订单服务出 现了问题，订单服务⼜⼀次发起调⽤库存服务，当订单服务传⼊的version还是1，再执⾏上⾯的sql语 句时，就不会执⾏；因为version已经变为2了，where条件就不成⽴。保证了不会重复提交。 乐观锁主要使⽤于处理读多写少的问题。

- 3.2.3 分布式锁


多个节点同时处理相同的数据，可以使⽤分布式锁，锁定此数据，处理完成后释放锁。获取到锁的必 须先判断这个数据是否被处理过。

- 3.3 各种唯⼀约束


- 3.3.1 数据库唯⼀约束

插⼊数据，应该按照唯⼀索引进⾏插⼊，⽐如订单号，相同的订单就不可能有两条相同的记录插⼊。 我们在数据库层⾯防⽌重复。 这个机制利⽤了数据库的主键唯⼀约束的特性，解决了在insert场景时幂等性等问题。但主键的要求不 是⾃增的主键，这样就需要业务⽣成全局唯⼀的主键。 如果是分库分表场景下，路由规则要保证相同请求下，落地在同⼀个数据库和同⼀表中，要不然数据 库主键约束就不起效果了，因为不同的数据库和表主键不相关。

- 3.3.2 redis set 防重


很多数据需要处理，只能被处理⼀次，我们可以计算数据的MD5，将其放⼊redis的set，每次处理数 据，先看这个MD5是否已存在，存在就不处理。

- 3.4 防重表

使⽤订单号orderNo作为去重表的唯⼀索引，把唯⼀索引插⼊去重表，再进⾏业务操作，且他们在同⼀ 个事务中。这个保证了重复请求时，因为去重表有唯⼀约束，导致请求失败，避免了幂等问题。 需要注意的是，去重表和业务表应该在同⼀库中，这样就保证了在同⼀个事务中，即使业务操作失败 了，也会把去重表的数据回滚。保证了数据⼀致性。

上述使⽤的redis防重表同理。

- 3.5 全局请求唯⼀id（可以处理feign重复调⽤，不能处理客户端重复提交）


调⽤接⼝时，⽣成⼀个唯⼀id，redis讲数据存储到集合中（去重），存在即处理过。 可以使⽤nginx设置每⼀个请求的唯⼀id； proxy_set_header X-Request-Id $request_id;
