Kafka、RocketMQ、RabitMQ⽐较

- 1.ActiveMQ


优点

单机吞吐量：万级

topic数量都吞吐量的影响：

时效性：ms级

可⽤性：⾼，基于主从架构实现⾼可⽤性

消息可靠性：有较低的概率丢失数据

功能⽀持：MQ领域的功能极其完备

缺点:

官⽅社区现在对ActiveMQ 5.x维护越来越少，较少在⼤规模吞吐的场景中使⽤。

- 2.Kafka


号称⼤数据的杀⼿锏，谈到⼤数据领域内的消息传输，则绕不开Kafka，这款为⼤数据⽽⽣的消息中间 件，以其百万级TPS的吞吐量名声⼤噪，迅速成为⼤数据领域的宠⼉，在数据采集、传输、存储的过程 中发挥着举⾜轻重的作⽤。

Apache Kafka它最初由LinkedIn公司基于独特的设计实现为⼀个分布式的提交⽇志系统( a distributed comit log)，之后成为Apache项⽬的⼀部分。

⽬前已经被LinkedIn，Uber, Twiter, Netflix等⼤公司所采纳。

优点

性能卓越，单机写⼊TPS约在百万条/秒，最⼤的优点，就是吞吐量⾼。

时效性：ms级

可⽤性：⾮常⾼，kafka是分布式的，⼀个数据多个副本，少数机器宕机，不会丢失数据，不会导致不 可⽤

消费者采⽤Pul⽅式获取消息, 消息有序, 通过控制能够保证所有消息被消费且仅被消费⼀次;

有优秀的第三⽅Kafka Web管理界⾯Kafka-Manager；

在⽇志领域⽐较成熟，被多家公司和多个开源项⽬使⽤；

功能⽀持：功能较为简单，主要⽀持简单的MQ功能，在⼤数据领域的实时计算以及⽇志采集被⼤规模 使⽤

缺点：

Kafka单机超过64个队列/分区，Load会发⽣明显的飙⾼现象，队列越多，load越⾼，发送消息响应时 间变⻓

使⽤短轮询⽅式，实时性取决于轮询间隔时间；

消费失败不⽀持重试；

⽀持消息顺序，但是⼀台代理宕机后，就会产⽣消息乱序；

社区更新较慢；

- 3.RabitMQ


RabitMQ 207年发布，是⼀个在AMQP(⾼级消息队列协议)基础上完成的，可复⽤的企业消息系统， 是当前最主流的消息中间件之⼀。

RabitMQ优点：

由于erlang语⾔的特性，mq 性能较好，⾼并发；

吞吐量到万级，MQ功能⽐较完备

健壮、稳定、易⽤、跨平台、⽀持多种语⾔、⽂档⻬全；

开源提供的管理界⾯⾮常棒，⽤起来很好⽤

社区活跃度⾼；

RabitMQ缺点：

erlang开发，很难去看懂源码，基本职能依赖于开源社区的快速维护和修复bug，不利于做⼆次开发和 维护。

RabitMQ确实吞吐量会低⼀些，这是因为他做的实现机制⽐较重。

需要学习⽐较复杂的接⼝和协议，学习和维护成本较⾼。

- 4.RocketMQ


RocketMQ出⾃ 阿⾥公司的开源产品，⽤ Java 语⾔实现，在设计时参考了 Kafka，并做出了⾃⼰的⼀ 些改进。

RocketMQ在阿⾥集团被⼴泛应⽤在订单，交易，充值，流计算，消息推送，⽇志流式处理，binglog 分发等场景。

可⽤性：⾮常⾼，分布式架构

功能⽀持：MQ功能较为完善，还是分布式的，扩展性好

⽀持10亿级别的消息堆积，不会因为堆积导致性能下降

源码是java，我们可以⾃⼰阅读源码，定制⾃⼰公司的MQ，可以掌控

RocketMQ缺点：

⽀持的客户端语⾔不多，⽬前是java及c+，其中c+不成熟；

社区活跃度⼀般

没有在 mq 核⼼中去实现JMS等接⼝，有些系统要迁移需要修改⼤量代码

消息队列选择建议

- 1.Kafka

Kafka主要特点是基于Pul的模式来处理消息消费，追求⾼吞吐量，⼀开始的⽬的就是⽤于⽇志收集和 传输，适合产⽣⼤量数据的互联⽹服务的数据收集业务。

⼤型公司建议可以选⽤，如果有⽇志采集功能，肯定是⾸选kafka了。

天⽣为⾦融互联⽹领域⽽⽣，对于可靠性要求很⾼的场景，尤其是电商⾥⾯的订单扣款，以及业务削 峰，在⼤量交易涌⼊时，后端可能⽆法及时处理的情况。

RoketMQ在稳定性上可能更值得信赖，这些业务场景在阿⾥双 1已经经历了多次考验，如果你的业务 有上述并发场景，建议可以选择RocketMQ。

- 3.RabitMQ


RabitMQ :结合erlang语⾔本身的并发优势，性能较好，社区活跃度也⽐较⾼，但是不利于做⼆次开 发和维护。不过，RabitMQ的社区⼗分活跃，可以解决开发过程中遇到的bug。

如果你的数据量没有那么⼤，⼩公司优先选择功能⽐较完备的RabitMQ。
