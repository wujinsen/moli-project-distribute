⽹络层 客户端通过创建到6379端⼝的TCP连接来连接到⼀个Redis服务器。每个Redis命令或者客户端和服务 器之间传输的数据都以\r\n (CRLF)结束。 请求 Redis可以接受由不同参数组成的命令。只要接收到⼀个命令，这个命令就会被执⾏，然后⼀个答复会 被返回给客户端。 新的统⼀请求协议 新的统⼀协议是在Redis1.2中引⼊的，但是在Redis2.0中成为了与Redis服务器交互的标准⽅式。在统 ⼀协议中所有发送到Redis服务器的参数都是⼆进制安全的。这是总体格式：

- *<number of arguments> CR LF $<number of bytes of argument 1> CR LF <argument data> CR LF

... $<number of bytes of argument N> CR LF <argument data> CR LF

- *3 $3 SET $5 mykey $7 myvalue

这是以上命令以带引号的字符串展现的样⼦，这样就可以看到这个请求中每个字节的准确内容：

"*3\r\n$3\r\nSET\r\n$5\r\nmykey\r\n$7\r\nmyvalue\r\n"

就像你⼀会将会看到的，这个格式还会被⽤在Redis回复中。这个被⽤于每个参数中的格式 $6\r\nmydata\r\n叫做Bulk 回复。Redis实际上使⽤的统⼀请求协议会返回内容列表，叫做

Multi-bulk 回复

。它是由N个不同的Bulk 回复合在⼀起，并且有⼀个字符串前缀*<argc>\r\n其中<argc>是后⾯参 数（Bulk回复）的数量。 回复

Redis会以不同类型的回复对命令进⾏响应。可以通过服务器发送的第⼀个字节来判定回复的类型：

如果是单⾏回复，那么第⼀个字节是「+」 如果回复的内容是错误信息，那么第⼀个字节是「 _ 」 如果回复的内容是⼀个整型数字，那么第⼀个字节是「:」 如果是bulk回复，那么第⼀个字节是「$」 如果是multi-bulk回复，那么第⼀个字节是「*」

状态回复 ⼀个状态回复（或者：单⾏回复）的格式是以「+」开头，以「\r\n」结束的单⾏字符串。举个例⼦：

+OK

客户端库要返回「+」后⾯的所有内容，这个例⼦⾥边是字符串「OK」。 错误回复 错误的发送⽅式和状态回复很像。唯⼀的不同是第⼀个字节⽤「-」替代了「+」。 错误回复只有当⼀ 些奇怪的事情发⽣时才会被发送，例如如果你想要⽤错误的数据类型执⾏⼀个操作，或者这个命令不 存在等等。所以客户端库应该在接收到⼀个错误回复的时候抛出⼀个异常。 整形回复 这个类型的回复就是⼀个代表整数以CRLF结束的字符串，并且⽤⼀个字节的字符「:」作为前缀。例如 「:0\r\n」，或者「:1 0\r\n」 都是整形回复。 像INCR或者LASTSAVE命令使⽤整型回复来返回⼀个 没有特别含义的整型数字。对于INCR来说返回的是增加后的数字，对于LASTSAVE来说是 ⼀个UNIX时 间等等。 像EXISTS这样的命令会返回1表示true，返回0表示false。 其他命令像SAD，SREM和 SETNX在操作实际完成的时候会返回1，否则返回0。 以下命令将会返回整型回复：SETNX, DEL, EXISTS, INCR, INCRBY, DECR, DECRBY, DBSIZE, LASTSAVE, RENAMENX, MOVE, LEN, SAD, SREM, SISMEMBER, SCARD Bulk回复 Bulk回复被服务器⽤来返回⼀个⼆进制安全的字符串。

C: GET mykey S: $6\r\nfoobar\r\n

服务器以这种⽅式来发送数据：第⼀⾏是⼀个字节的内容「$」，之后跟着具体内容的字节数，接下来 是CRLF，然后具体数据内容被发送，接下来是额外的两个字节的CRLF。服务器实际发送的序列是：

"$6\r\nfoobar\r\n"

如果请求的内容不存在，那么bulk回复将会使⽤特殊值-1作为数据⻓度，例如：

C: GET nonexistingkey S: $-1

当请求对象不存在，客户端库API不要返回⼀个空字符串，应该是⼀个nil对象。举个例⼦⼀个Ruby库应 该返回「nil」，⼀个C库应该返回NUL（或者在回复对象中设置⼀个特殊标记），等等。

Multi-bulk回复 像LRANGE这类的命令需要返回多个值（列表中的每个元素是⼀个值，LRANGE需要返回多个元素）。 这通过multiple bulk write来实现，其第⼀⾏指明后⾯有多少个bulk write。⼀个multi bulk回复的第⼀ 个字节⼀直是*。例如：

C: LRANGE mylist 0 3 s: *4 s: $3 s: foo s: $3 s: bar s: $5 s: Hello s: $5 s: World

就像你看到的，multi bulk 回复和使⽤统⼀协议发送命令到Redis服务器使⽤的是同样的格式。 服务器 发送的第⼀⾏是*4\r\n，⽤来指出下⾯将会有四个bulk回复。然后每个bulk write将会被传送。 如果指 定的key不存在，那么这个key被认为拥有⼀个空列表，然后0会做为multi bulk的数量被发送。例如：

C: LRANGE nokey 0 1 S: *0

当 命令超时，它将返回值为nil的multi bulk回复。这个类型的multi bulk的数量为-1并且应该被 解释为nil值。例如：

## BLPOP

C: BLPOP key 1 S: *-1

当这个发⽣的时候，⼀个客户端库API应该返回⼀个nil对象⽽不是⼀个空列表。区分⼀个空的列表和⼀ 个错误条件（⽐如 命令的超时条件）是必要的。 Multi-Bulk回复中的Nil元素 ⼀个multi bulk 回复的单个元素可能会存在-1的⻓度，⽤来指明这个元素不存在并且不是空字符串。 这个可能发⽣在启⽤了GET模式选项的SORT命令，并且指定的key不存在。包含⼀个空元素的multi bulk回复的例⼦：

## BLPOP

S: *3 S: $3 S: foo S: $-1 S: $3 S: bar

第⼆个元素是nil。客户端库需要返回如下内容：

["foo",nil,"bar"]

多个命令和管道 ⼀个客户端可以使⽤相同的连接来发送多个命令。Redis是⽀持管道的，所以客户端可以通过⼀次写操 作发送多个命令，不需要读取服务器的回复才能发 送下⼀个命令。所有的回复可以在最后读取。 通常 情况下Redis服务器和客户端之间会有⾮常快的连接，所以客户端⽀持这个特性不是那么重要，但如果 ⼀个应⽤需要在很短的时间⾥发送⼤量的命令那么使 ⽤管道将会⾮常快。 发送命令的旧协议 在统⼀请求协议之前，Redis使⽤⼀个不同的协议来发送命令，这个协议仍然被⽀持因为通过telnet它 很容易⼿写。在这个协议中存在两种命令：

inline 命令: 命令很简单，就是⽤空格把参数分隔开来的字符串。⼆进制安全是不可能的。

Bulk 命令: bulk命令和inline命令⼏乎是⼀样的，但是最后⼀个参数为了能够接受⼆进制安全的内 容，所以需要以特殊的⽅式进⾏处理。

Inline命令 向Redis发送命令最简单的⽅法是使⽤inline命令。以下是⼀个服务器/客户端之间使⽤inline命令进⾏交 互的例⼦（服务器以S:作为开始，客户端以C:作为开始）

C: PING S: +PONG

以下是另⼀个例⼦，⼀个返回整数的inline命令：

C: EXISTS somekey S: :0

由于「somekey」不存在，所以服务器返回「:0」。 注意EXISTS命令只带有⼀个参数。多个参数以空 格进⾏分隔。 Bulk命令 当⼀些命令以inline命令发送的时候为了使最后⼀个参数⽀持⼆进制安全，需要以⼀个特殊的格式发 送。这些命令将会把最后⼀个参数作为「字节计数器」，然后⼤量的数据会被发送（这些数据可以为 ⼆进制安全，因为服务器知道有多少字节需要读取）。 看下⾯这个例⼦：

C: SET mykey 6 C: foobar S: +OK

这个命令的最后⼀个参数是「6」。这个指明了后⾯数据，字符串「fobar」的字节数。注意即使这些 数据被额外的⼆个字节⼤⼩的CRLF所截断。 所有bulk命令的准确格式是：把最后⼀个参数替换成后⾯ 数据的字节数，接下来是数据本身和CRLF。为了能够让程序员更加清晰的理解，这是上⾯例⼦中客 户 端发送的字符串：

"SET mykey 6\r\nfoobar\r\n"

Redis有⼀个内部的列表，记录了什么命令是inline，什么命令是bulk，所以你需要参考这个来发送命 令。强烈推荐使⽤新的统⼀请求协议来替代旧的协议。 原⽂：
