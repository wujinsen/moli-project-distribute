## 库存扣减

![image 8](<实战！如何从零搭建10万级 QPS 大流量、高并发优惠券系统(同步发生冲突).note_images/imageFile8.png>)

这⾥还剩下⼀个问题，即：扣减⼦库存，每次都是从 1 开始进⾏的话，那对 Redis 对应分⽚的压⼒其 实并没有减轻，因此，我们需要做到：每次请求，随机不重复的轮询⼦库存。以下是本项⽬采取的⼀ 个具体思路： Redis ⼦库存的 key 的最后⼀位是分⽚的编号，如： x_stock_key1、 x_stock_key2…，在扣减⼦ 库存时，我们先⽣成对应分⽚总数的随机不重复数组，如第⼀次是[1,2,3]，第⼆次可能是[3,1,2]，这 样，每次扣减⼦库存的请求，就会分布到不同的 Redis 分⽚上，缓轻 Redis 单分⽚压⼒的同时，也能 ⽀持更⾼ QPS 的扣减请求。 这种思路的⼀个问题是，当我们库存接近耗尽的情况下，很多分⽚⼦库存的轮询将变得毫⽆意义，因 此我们可以在每次请求的时候，将⼦库存的剩余量记录下来，当某⼀个券模板的⼦库存耗尽后，随机 不重复的轮询操作直接跳过这个⼦库存分⽚，这样能够优化系统在库存即将耗尽情况下的响应速度。 业界针对 Redis 热点 key 的处理，除了分 key 以外，还有⼀种 key 备份的思路：即，将相同的 key， ⽤某种策略备份到不同的 Redis 分⽚上去，这样就能将热点打散。这种思路适⽤于那种读多写少的场 景，不适合应对发券这种⼤流量写的场景。在⾯对具体的业务场景时，我们需要根据业务需求，选⽤ 恰当的⽅案来解决问题。

# 券模板获取失败问题及解决⽅案

问题

⾼ QPS，⾼并发的场景下，即使我们能将接⼝的成功率提升 0.01%，实际表现也是可观的。现在回过 头来看下整个发券的流程：查券模板（Redis）–>校验–>幂等（MySQL）–> 发券（MySQL）。在查券 模板信息时，我们会请求 Redis，这是强依赖，在实际的观测中，我们会发现，Redis 超时的概率⼤概 在万分之 2、3。因此，这部分发券请求是必然失败的。 解决⽅案 为了提⾼这部分请求的成功率，我们有两种⽅案。 ⼀是从 Redis 获取券模板失败时，内部进⾏重试；⼆是将券模板信息缓存到实例的本地内存中，即引 ⼊⼆级缓存。 内部重试可以提⾼⼀部分请求的成功率，但⽆法从根本上解决 Redis 存在超时的问题，同时重试的次 数也和接⼝响应的时⻓成正⽐。⼆级缓存的引⼊，可以从根本上避免 Redis 超时造成的发券请求失 败。因此我们选⽤⼆级缓存⽅案：
