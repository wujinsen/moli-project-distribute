⼀.各个版本的Redis分布式锁

- 1. V1.0

这个版本应该是最简单的版本，也是出现频率很⾼的⼀个版本，⾸先给锁加⼀个过期时间操作是为了 避免应⽤在服务重启或者异常导致锁⽆法释放后，不会出现锁⼀直⽆法被释放的情况。

这个⽅案的⼀个问题在于每次提交⼀个Redis请求，如果执⾏完第⼀条命令后应⽤异常或者重启，锁将 ⽆法过期，⼀种改善⽅案就是使⽤Lua脚本（包含SETNX和EXPIRE两条命令），但是如果Redis仅执⾏ 了⼀条命令后crash或者发⽣主从切换，依然会出现锁没有过期时间，最终导致⽆法释放。

另外⼀个问题在于，很多同学在释放分布式锁的过程中，⽆论锁是否获取成功，都在finaly中释放锁， 这样是⼀个锁的错误使⽤，这个问题将在后续的V3.0版本中解决。

针对锁⽆法释放问题的⼀个解决⽅案基于GETSET命令来实现

- 2. V1.1 基于GETSET


思路：

SETNX(Key,ExpireTime)获取锁

如果获取锁失败，通过GET(Key)返回的时间戳检查锁是否已经过期

GETSET(Key,ExpireTime)修改Value为NewExpireTime

检查GETSET返回的旧值，如果等于GET返回的值，则认为获取锁成功

注意：这个版本去掉了EXPIRE命令，改为通过Value时间戳值来判断过期

问题：

在锁竞争较⾼的情况下，会出现Value不断被覆盖，但是没有⼀个Client获取到锁

在获取锁的过程中不断的修改原有锁的数据，设想⼀种场景C1，C2竞争锁，C1获取到了锁，C2锁 执⾏了GETSET操作修改了C1锁的过期时间，如果C1没有正确释放锁，锁的过期时间被延⻓，其它 Client需要等待更久的时间

- 3. V2.0 基于SETNX

Redis 2.6.12版本后SETNX增加过期时间参数，这样就解决了两条命令⽆法保证原⼦性的问题。但是设 想下⾯⼀个场景：

C1成功获取到了锁，之后C1因为GC进⼊等待或者未知原因导致任务执⾏过⻓，最后在锁失效前C1没有 主动释放锁 2. C2在C1的锁超时后获取到锁，并且开始执⾏，这个时候C1和C2都同时在执⾏，会因重 复执⾏造成数据不⼀致等未知情况 3. C1如果先执⾏完毕，则会释放C2的锁，此时可能导致另外⼀个 C3进程获取到了锁

- 4. V3.0


由于C1的停顿导致C1 和C2同都获得了锁并且同时在执⾏，在业务实现间接要求必须保证幂等性

C1释放了不属于C1的锁

这个⽅案通过指定Value为时间戳，并在释放锁的时候检查锁的Value是否为获取锁的Value，避免了 V2.0版本中提到的C1释放了C2持有的锁的问题；另外在释放锁的时候因为涉及到多个Redis操作，并 且考虑到Check And Set 模型的并发问题，所以使⽤Lua脚本来避免并发问题。

存在问题：

如果在并发极⾼的场景下，⽐如抢红包场景，可能存在UnixTimestamp重复问题，另外由于不能保证 分布式环境下的物理时钟⼀致性，也可能存在UnixTimestamp重复问题，只不过极少情况下会遇到。

- 5. V3.1


Redis 2.6.12后SET同样提供了⼀个NX参数，等同于SETNX命令，官⽅⽂档上提醒后⾯的版本有可能去 掉SETNX, SETEX, PSETEX,并⽤SET命令代替，另外⼀个优化是使⽤⼀个⾃增的唯⼀UniqId代替时间 戳来规避V3.0提到的时钟问题。

这个⽅案是⽬前最优的分布式锁⽅案，但是如果在Redis集群环境下依然存在问题：

由于Redis集群数据同步为异步，假设在Master节点获取到锁后未完成数据同步情况下Master节点 crash，此时在新的Master节点依然可以获取锁，所以多个Client同时获取到了锁

# ⼆.分布式Redis锁：Redlock

V3.1的版本仅在单实例的场景下是安全的，针对如何实现分布式Redis的锁，国外的分布式专家有过激 烈的讨论， antirez提出了分布式锁算法Redlock，在distlock话题下可以看到对Redlock的详细说明， 下⾯是Redlock算法的⼀个中⽂说明（引⽤）

假设有N个独⽴的Redis节点

获取当前时间（毫秒数）。

按顺序依次向N个Redis节点执⾏获取锁的操作。这个获取操作跟前⾯基于单Redis节点的获取锁的 过程相同，包含随机字符串my_random_value，也包含过期时间(⽐如PX 3 0，即锁的有效时 间)。为了保证在某个Redis节点不可⽤的时候算法能够继续运⾏，这个获取锁的操作还有⼀个超时 时间(time out)，它要远⼩于锁的有效时间（⼏⼗毫秒量级）。客户端在向某个Redis节点获取锁失 败以后，应该⽴即尝试下⼀个Redis节点。这⾥的失败，应该包含任何类型的失败，⽐如该Redis节 点不可⽤，或者该Redis节点上的锁已经被其它客户端持有（注：Redlock原⽂中这⾥只提到了 Redis节点不可⽤的情况，但也应该包含其它的失败情况）。

计算整个获取锁的过程总共消耗了多⻓时间，计算⽅法是⽤当前时间减去第1步记录的时间。如果客 户端从⼤多数Redis节点（>= N/2+1）成功获取到了锁，并且获取锁总共消耗的时间没有超过锁的 有效时间(lock validity time)，那么这时客户端才认为最终获取锁成功；否则，认为最终获取锁失 败。

如果最终获取锁成功了，那么这个锁的有效时间应该重新计算，它等于最初的锁的有效时间减去第 3步计算出来的获取锁消耗的时间。

如果最终获取锁失败了（可能由于获取到锁的Redis节点个数少于N/2+1，或者整个获取锁的过程消 耗的时间超过了锁的最初有效时间），那么客户端应该⽴即向所有Redis节点发起释放锁的操作（即 前⾯介绍的Redis Lua脚本）。

释放锁：对所有的Redis节点发起释放锁操作

然⽽Martin Klepman针对这个算法提出了质疑，提出应该基于fencing token机制（每次对资源进⾏ 操作都需要进⾏token验证）

Redlock在系统模型上尤其是在分布式时钟⼀致性问题上提出了假设，实际场景下存在时钟不⼀致 和时钟跳跃问题，⽽Redlock恰恰是基于timing的分布式锁

另外Redlock由于是基于⾃动过期机制，依然没有解决⻓时间的gc pause等问题带来的锁⾃动失 效，从⽽带来的安全性问题。

接着antirez⼜回复了Martin Klepman的质疑，给出了过期机制的合理性，以及实际场景中如果出现 停顿问题导致多个Client同时访问资源的情况下如何处理。

针对Redlock的问题，基于Redis的分布式锁到底安全吗给出了详细的中⽂说明，并对Redlock算法存在 的问题提出了分析。

# 总结

不论是基于SETNX版本的Redis单实例分布式锁，还是Redlock分布式锁，都是为了保证下特性

安全性：在同⼀时间不允许多个Client同时持有锁

活性

死锁：锁最终应该能够被释放，即使Client端crash或者出现⽹络分区（通常基于超时机制）

容错性：只要超过半数Redis节点可⽤，锁都能被正确获取和释放

所以在开发或者使⽤分布式锁的过程中要保证安全性和活性，避免出现不可预测的结果。

另外每个版本的分布式锁都存在⼀些问题，在锁的使⽤上要针对锁的实⽤场景选择合适的锁，通常情 况下锁的使⽤场景包括：

Eficiency(效率)：只需要⼀个Client来完成操作，不需要重复执⾏，这是⼀个对宽松的分布式锁，只需 要保证锁的活性即可；

Corectnes(正确性)：多个Client保证严格的互斥性，不允许出现同时持有锁或者对同时操作同⼀资 源，这种场景下需要在锁的选择和使⽤上更加严格，同时在业务代码上尽量做到幂等

在Redis分布式锁的实现上还有很多问题等待解决，我们需要认识到这些问题并清楚如何正确实现⼀个 Redis 分布式锁，然后在⼯作中合理的选择和正确的使⽤分布式锁。
