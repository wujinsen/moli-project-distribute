# Harbor仓库

Kuternetes 企业级 Docker 私有仓库 Harbor ⼯具。

Harbor 的每个组件都是以 Docker 容器的形式构建的，使⽤ Docker Compose 来对它进⾏部署。⽤于 部署 Harbor 的 Docker Compose 模板位于 /Deployer/docker-compose.yml 中，其由 5 个容器组成， 这⼏个容器通过 Docker link 的形式连接在⼀起，在容器之间通过容器名字互相访问。对终端⽤户⽽ ⾔，只需要暴露 Proxy(即Nginx) 的服务端⼝即可。

Proxy

由Nginx服务器构成的反向代理

Registry

由Docker官⽅的开源官⽅的开源Registry镜像构成的容器实例

UI

即架构中的core services服务，构成此容器的代码是Harbor项⽬的主体

MySQL

由官⽅MySQL镜像构成的数据库容器

Log

运⾏着rsyslogd的容器，通过log-driver的形式收集其他容器的⽇志

详细介绍与搭建步骤请参考：企业级环境中基于 Harbor 搭建

资源清单

K8S 中所有的内容都抽象为了资源，资源实例化之后就叫做对象。

在 Kubernetes 系统中，Kubernetes对象是持久化的实体，Kubernetes使⽤这些实体去表示整个集群 的状态。特别地，它们描述了如下信息：

Kubernetes 对象是 “⽬标性记录” ⸺ ⼀旦创建对象，Kubernetes 系统将持续⼯作以确保对象存在。 通过创建对象，本质上是在告知 Kubernetes 系统，所需要的集群⼯作负载看起来是什么样⼦的，这就 是 Kubernetes 集群的期望状态。

有这样⼀个需求，就是集群中多台服务的配置是不⼀致的。这就导致资源分配并不是均匀的，⽐如我 们需要有些服务节点⽤来运⾏计算密集型的服务，⽽有些服务节点来运⾏需要⼤量内存的服务。⽽在

- k8s 中当然也配置了相关服务来处理上述的问题，那就是 Scheduler。


Scheduler 是 kubernetes 的调度器，主要的任务是把定义的 Pod 分配到集群的节点上。听起来⾮常简 单，但有很多要考虑的问题：

公平

如何保证每个节点都能被分配资源

资源⾼效利⽤

集群所有资源最⼤化被使⽤

效率

调度的性能要好，能够尽快地对⼤批量的 Pod 完成调度⼯作

灵活

允许⽤户根据⾃⼰的需求控制调度的逻辑

Scheduler 是作为单独的程序运⾏的，启动之后会⼀直坚挺 API Server，获取 PodSpec.NodeName 为 空的 Pod，对每个 Pod 都会创建⼀个 binding，表明该 Pod 应该放到哪个节点上。

kubectl 使⽤指南

kubectl 是 Kubernetes ⾃带的客户端，可以⽤它来直接操作 Kubernetes 集群。

⽇常在使⽤ Kubernetes 的过程中，kubectl ⼯具可能是最常⽤的⼯具了，所以当我们花费⼤量的时间 去研究和学习 Kuernetes 的时候，那么我们就⾮常有必要去了解下如何⾼效的使⽤它了。

从⽤户⻆度来说，kubectl 就是控制 Kubernetes 的驾驶舱，它允许你执⾏所有可能的 Kubernetes 操 作；从技术⻆度来看，kubectl 就是 Kubernetes API 的⼀个客户端⽽已。

Kubernetes API 是⼀个 HTP REST API 服务，该 API 服务才是 Kubernetes 的真正⽤到的⽤户接⼝， 所以 Kubernetes 通过该 API 进⾏实际的控制。这也就意味着每个 Kubernetes 的操作都会通过 API 端 点暴露出去，当然也就可以通过对这些 API 端⼝进⾏ HTP 请求来执⾏相应的操作。所以，kubectl 最 主要的⼯作就是执⾏ Kubernetes API 的 HTP 请求。
