# 微服务是什么？

微服务是⼀种细粒度（Fine-Grain）的SOA

个⼈认为，与其说微服务是⼀种技术，不如将其定义为⼀种架构，⽽架构则是“技”的实现与“术”的策略 相辅相成。“术”的策略需要分析使⽤场景，进⾏合理地划分业务边界，实现“业以类聚”，然⽽“技”的实 现则通过特定的技术在实现业务逻辑之时，更多的考虑实现过程中的效率性、测试的便利性、维护的 可持续性，达到“技以群分”的⽬的。 由此⽽论，我个⼈偏好将其定义为：“微服务是⼀种细粒度的SOA”。 这样定义的好处在于，没必要去重复地“抹⿊”“单体应⽤”（Monolithic，也有⼈翻译成“巨⽯应⽤”），缘 于SOA技术的衍化过程中早已提及。那么，细粒度更多的体现在“取其精华，去其糟粕”。

# 为什么要微服务？

效率的需要

应⽤进⾏微服务化后，规模和体积变得更加轻量级，在编译、打包、分发、部署等环节节约了时间， 开发上效率提升。

质量的需要

微服务应⽤⾯向持续集成友好，⾃动化编译、单元和集成测试⽤例执⾏和回归，提⾼应⽤整体质量。

稳定的需要

当应⽤⼤⽽全时，往往牵⼀发⽽动全身，其中⼀个服务出现问题，整体受到牵动效应。整体稳定性得 不到保证，因此，经过微服务化后，应⽤由原来的服务内部组装到服务⾃由组合，⼀旦关联服务存在 问题，整体应⽤可以选择性地降级或熔断等措施，待问题服务恢复，⼀切照常执⾏。

运维的需要

微服务应⽤具备⾃动化编译、打包、分发、部署和运维的能⼒。传统的应⽤不但需要开发、还需要测 试和运维⼈员，微服务应⽤实现后，将理想化的全栈（Full-Stack）⼯程师变为可能。

成⻓的需要

微服务能够更好，更快地适配新技术，⽐如⽬前流⾏的Apache Kafka。⽽⼯程⼈员需要接触新的技 术，为未来可能的技术选型做好准备。我的建议在⼀些不那么重要的微服务应⽤中，可以尝试⼀些新 的技术，在其提供的功能与实际需要之间，找到⼀些⾃⼰的理解，也是⾃我成⻓的需要。

# 为什么不必微服务？

论语有⾔：“⼦绝四：‘毋意、毋必、毋固、毋我’。”，简单地说，不要臆断，不要固执，不要⾃我感觉 良好，也有什么是必定的。那么，在微服务实践过程中，哪些因素可以不必微服务呢？请注意⽤词， 这⾥说的是“不必”，不是“不要”。

场景单⼀

当应⽤的场景单⼀时，没有必要⾮得微服务，因为它本身就是微服务，例如⼀些静态的通告⻚⾯。

逻辑简单

当应⽤逻辑简单时，同样也违背了微服务的初衷，因为微服务是为了解决复杂业务逻辑⽽衍⽣，因此 这种情况下也不必实施微服务。

业务渐逝

⾸先，我解释⼀下“渐逝”，也就是逐渐消逝的意思。当应⽤所关注的业务趋于消逝状态时，尽管有实施 的空间，但⽆实施的必要。因为这样的应⽤随时可能不复存在，好⽐没有必要去对BB机或者短信业务 ⼤张旗⿎的重构⼀般。

“⽼成持重”

⽼成持重的原意是形容⼈做事情⽼练和沉稳。这⾥我引⽤了这个成语，是为了⽅便记忆，需要将其拆 开，单独解释。 “⽼”是指年⽼的应⽤，多久算得上年⽼呢？个⼈经验，应⽤服役年龄超过三年以上。 “成”则表示应⽤的规模已成形，业务上⼏乎不再变化，⽐如通知应⽤。 “持”说明应⽤的场景还将持续较⻓时间。

“重”表示应⽤所处的位置举⾜轻重，不能随时重构，⽐如交易应⽤。 当应⽤符合其中⼀条以上的特征时，该应⽤不必实⾏微服务。

技术盲从

这⼀点是我最为关注，也是最担⼼朋友触犯的。我们同为⼯程⼈员，对技术的追求毋容置疑，可是千 万不能因为技术⽽技术，新的技术推出或是解决现有问题，或是提供便利性，可是也有夸⼤其词的成 分。理性地评估和谨慎地实施，更是我们更要关注的地⽅。技术困难挑战聪明才智，理智对待则考验 情绪控制。

技术

技术上，基本上也是以下三个套路：

Docker DDD Middleware（Java）

DDD

DDD是Domain Driven Design（领域驱动设计）的简写，该技术源于Eric Evans 在其名著《Domain Driven Design》。从年代来看，已是相当⽼的设计⽅法论了。它作为微服务重要的理论依据，如今⼜ 如“凤凰涅槃”⼀般，重新进⼊软件领域的视野。DDD的三⼤实施策略在具体微服务实践过程中，取⼆舍 ⼀。当然，整个DDD的理论并不限于此，个⼈理解，DDD好像是⼀个传说，⼤家都听说过，但是谁也 没有⻅到过。⽽是实现这种理想就如同乌托邦式的“共产主义”，⽬前仍未到时候。

有界上下⽂（Bounded Context）

有界上下⽂的思想，个⼈认为是在《设计模式》中的“单职责原则”进⼀步发展⽽⾔。其实也体现了东⻄ ⽅⽂化的差异，东⽅是以古代中国为代表的“中央集权”思想，和古希腊城邦的“三权分⽴”的⺠治思想。 微服务则属于“权⼒分⽴”思想的范畴。在微服务实践过程中，确定应⽤边界是必要的，也是困难的。必 要性反应在系统职责划分，要简约、清晰，不耦合。困难性则体现在重构过程不是⼀蹴⽽就，⽽是循 序渐进，同时，应⽤还伴随着业务发展⽽同步开发，其间的困难是可预知的。虽然过程是痛苦的，但 是也不得不去做。

持续集成（Continuous integration）

持续集成是继承了TDD（Test Driven Development，测试驱动开发）的思想，对应形成规模的公司⽽ ⾔，基本上都部署了持续集成的环境，在阿⾥则是Aone 系统来统筹。⼀些流⾏的开源软件，如 GitLab、Jenkins（Hudson）等。

上下⽂映射（Context Map）

以上两个策略均在实践中被采纳，那么上下⽂映射（Context Map）则被舍弃，舍弃的原因并不在于其 不合理，⽽是难以驾驭。例如，⽤户服务提供⽤户的模型，其中包括了姓名、⽣⽇、电话等。可是下 游系统，需要仅仅需要⽤户的姓名信息，⽽实际情况，⽤户服务⽆法提供这么细粒度的服务，那么不 得不在中间做⼀层上下⽂映射，将两者不再直接关联。这种情况貌似还看不出端倪，可是为服务化 后，服务数量众多，其映射环节基本上不可控制，下游系统配合改动也是代价颇⾼，因此，在实践过 程中，还是保持原有的调⽤关系。尽量做到改造过程中，减低错误率。

JSP属于Java EE规范，因此Java EE均提供了实现，⽐如 Tomcat、Jetty、WebLogic 等等。因此， JSP 具备天然性兼容，不需要额外引⼊其他资源。

性能优秀

JSP属于解释编译型模板语⾔，⽆论是 Scriptlets 还是 EL 均可以翻译成 Java 源⽂件，然后将 Java 源 ⽂件编译成 Java Class ⽂件，再经过容器加载并且执⾏相关⽅法调⽤（可参考 org.apache.jasper.servlet.JspServlet）。

多种⻚⾯结构化

这个特点是很多国内 Java ⼯程⼈员不太关注的特性，通常将JSP⻚⾯结构定格在HTML，实际上，它 的⻚⾯结构格式可以设置成更为严格的XHTML，甚⾄是XML。顺便提⼀句，Thymeleaf 也具备该能 ⼒，⽽ Velocity 不具备。因此，在我看来，JSP 并不是太落伍，⽽是太超前。 缺点：

限制表达式（EL）

EL 的实现是OGNL 表达式的⼦集，仅实现了简单地数据读取和逻辑运⾏。类似于 Bean ⽅法调⽤这样 的⾼级语法，需要配合 JSF 这样的Web技术来配合（ JSF 叫座不叫好的 Web 框架 ）。

扩展繁琐

JSP 扩展主要是JSP 标签扩展，JSP 标签扩展被很多⼈视为反模式，我倒不怎么认为，但是对其配置 上倒是颇为复杂，举个例⼦，每个 Tag 的属性需要绑定⼀个对应的实现类属性，并且类型复杂，功能 各异，⽐如 IterationTag 和 BodyTag 的作⽤存在⼀定的区别。

规约较多

JSP 除了tag lib的规约以外，还有jsp-property-group 等，我⽤⼀段web.xml中的配置为例：

<jsp-config>

<taglib> <taglib-uri>http://tae-sdk.taobao.com/taglibs/sdk</taglib-uri> <taglib-location>/META-INF/config/taglibs/sdk-web-1.0.tld</taglib-location>

</taglib> <jsp-property-group>

<url-pattern>*.jsp</url-pattern> <page-encoding>GBK</page-encoding> <include-coda>/WEB-INF/jsp/coda/footer.jspf</include-coda> <trim-directive-whitespaces>true</trim-directive-whitespaces>

</jsp-property-group> </jsp-config>

Servlet强依赖

JSP 对于 Servlet API 是强依赖的，主要执⾏逻辑与Servlet 相同（ init ⽅法、service ⽅法以及 destroy ⽅法 ），在现代化的Java Web 编程模式中，基本上屏蔽了Servlet API接⼝，⽐如 Spring WebMVC 中的@RequestParam ⽤于获取请求参数，去取代Servlet API中的 javax.servlet.http.HttpServletRequest#getParameter(String) ⽅法，因为该⽅法仅返回 String 类型，如 要转化成 Integer 类型，不得不调⽤ Integer#valueOf(String) ⽅法进⾏转化。再则，⽬前流⾏的HTTP 2 Web服务器 - Undertow 并不兼容 Servlet API ⽅案。 接下来，进⼊Spring Cloud的部分。

Spring Cloud

Spring Cloud 官⽅提供了基本功能描述，其中包括：

分布式/版本化配置（Distributed/versioned configuration） 注册与发现（Registry and Discovery） 路由（Routing） 服务调⽤（Service-to-service calls） 负载均衡（Load balancing） 短路（ Circuit Break ） 分布式消息（Distributed messaging）
