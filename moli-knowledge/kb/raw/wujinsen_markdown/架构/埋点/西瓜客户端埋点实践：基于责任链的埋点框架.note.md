⽆埋点

⽆埋点是业界流⾏的⼀种埋点⽅案，所谓的“⽆埋点”、“全埋点”，是指埋点 SDK 通过编译时插桩、 运⾏时反射或动态代理的⽅式，⾃动进⾏埋点事件的触发和上报，⽆须客户端⼯程师⼿动进⾏埋点开 发⼯作。由产品经理、数据分析师等在埋点管理后台，使⽤ XPath 路径、⻚⾯视图 id 或者⽂本匹配 等技术，定位到⻚⾯视图的位置，过滤出所需的数据。

此⽅案的优势很明显，客户端只需要⼀次性的接⼊，理论上能够搜集到所有⻚⾯、视图的曝光、点击 等事件，⽆需客户端同学进⾏后续的埋点需求开发。

有这么好的事？为什么字节没有⼴泛使⽤？此⽅案的缺陷在于：

仅能上报有限的简单事件类型，如⻚⾯视图曝光、点击等，⽆法完成复杂事件的上报，如⼀次⽀付⾏ 为的操作路径、结果、错误信息等

⽆法⾃定义参数，主要指跳转的来源、所处的场景等上下⽂信息，⽆法满⾜复杂的数据分析和推荐模 型所需的数据要求

由产品经理、数据分析师等在埋点管理后台进⾏的事件录⼊，把复杂度从开发转嫁给了产品，消费成 本较⾼

对⻚⾯视图的稳定性有很⾼的要求，需要约定 id、⽂本、视图的层级，保持⻚⾯结构不变，如果客 户端⼯程师因为⼀些新需求开发、性能优化等调整了视图结构，将会导致已录⼊的埋点失效，增加了 额外的维护成本

全场景的数据上报，可能产⽣⼤量的⽆⽤数据，消耗⼤量传输、存储、计算资源

总结下这个⽅案的优势和问题：

优势 埋点需求对原有的功能代码侵⼊性⼩，只需实现 ITrackNode 接⼝建⽴链路，或者直接使⽤ ViewTre 的责任链，就可以达到跨层级传参的⽬的，传参复杂度⼤⼤降低，减少代码量和⼈⼒成本

各个节点不再需要关注其他节点的埋点参数，只需要负责填充⾃⼰的参数即可，做到“关注点分 离”，同时还能够让每个节点的参数得到复⽤，⽆需反复添加同样的参数，理想情况下，⼀个场景的 ⼀个新增参数，只需在相关节点上添加⼀处，即可做到所有的⼦节点都能收集到

问题 理解成本，就像前端同学使⽤ React ⼀样，不可避免地有⼀些学习成本；同时还需要和数据分析师 约定好埋点规范，只有在良好的规范下，埋点框架才能发挥更好的作⽤

⽆法通过类、参数定义等⽅式，强制约束埋点参数列表，新来的开发同学做新需求时，可能不知道该 传哪些参数

重构现有埋点的建议 ⼀些场景已经有⼤量埋点逻辑，⽆法短时间全部改掉。主要原因是因为埋点往往没有“边界”：埋点 需要⼤量的“上下⽂”与“来源”参数，⽽我们已经在实践中发现，这些参数是埋点错综复杂的主要原 因。

举 2 个例⼦：进⼊个⼈主⻚埋点（enter_pgc）和点击关注埋点(rt_folow)，开发⾯临的情况是进 ⼊个⼈主⻚的⼊⼝有 10+处，关注组件被引⽤的场景有 58 处。短时间要修改全部来源参数和上下 ⽂参数的传递⽅式，开发和测试成本很⼤，⼀次迭代基本不可能完成。

因此我们建议弄清埋点的“边界”，在此基础上控制每⼀次重构的影响范围。

重构通⽤业务组件 通⽤业务组件指的是像“关注按钮”或者“关注操作”这种有特定业务逻辑、⼤量使⽤于各种业务场景 的下沉组件。这类组件往往有特定的埋点要求，触发埋点本身不是很复杂的事情，复杂的是怎么获取 到触发事件时的上下⽂信息。对于此类组件，建议：

保留新旧两种埋点传参的接⼝

在⽼接⼝中对埋点参数进⾏封装，转发到新接⼝执⾏实际的逻辑，同时对⽼接⼝标注@Deprecated

未来逐步替换到新接⼝上

重构⼀个⻚⾯的结构 重构⼀个⻚⾯时，期望可以把各个层级定义成 TrackNode 节点，构建完整的责任链。但是⼀个⻚⾯ 结构中，常常使⽤了⼤量其他模块的组件或者功能，⽽依赖的这些模块还没完成埋点重构。因此重构 时依赖到其他模块/组件的情况，建议：

对当前模块内的部分构建责任链

不改变其他模块的接⼝，涉及到这些模块埋点参数传递的，在传参的节点上，获取节点的埋点参数， 使⽤⽼的⽅式传参

重构⼀个⻚⾯的来源传参⽅式 ⼀个⻚⾯的来源参数，外部可能通过很多种⽅式，如 Intent、单例等传递过来。为了让⻚⾯内责任 链上的每个节点，都能够获取到来源的参数，同时兼容外部新⽼传参的⽅式，建议：

当前⻚⾯改造成新的获取来源参数的⽅式，同时⽀持按照⽼的传参⽅式读取来源参数，需要时可在⻚ ⾯初始化的时机 Mock ⼀个 refererTrackNode

外部跳转逐步切换到新的来源参数传参⽅式
