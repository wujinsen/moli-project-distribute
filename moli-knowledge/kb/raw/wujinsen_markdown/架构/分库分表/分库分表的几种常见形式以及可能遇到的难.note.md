# ⽔平分表

⽔平分表也称为横向分表，⽐较容易理解，就是将表中不同的数据⾏按照⼀定规律分布到不同的数据 库表中（这些表保存在同⼀个数据库中），这样来降低单表数据量，优化查询性能。最常⻅的⽅式就 是通过主键或者时间等字段进⾏Hash和取模后拆分。如下图所示：

## 跨库join的问题

在拆分之前，系统中很多列表和详情⻚所需的数据是可以通过sql join来完成的。⽽拆分后，数据库可 能是分布式在不同实例和不同的主机上，join将变得⾮常麻烦。⽽且基于架构规范，性能，安全性等⽅ ⾯考虑，⼀般是禁⽌跨库join的。那该怎么办呢？⾸先要考虑下垂直分库的设计问题，如果可以调整， 那就优先调整。如果⽆法调整的情况，下⾯笔者将结合以往的实际经验，总结⼏种常⻅的解决思路， 并分析其适⽤场景。

## 跨库Join的⼏种解决思路

# 垂直分库总结和实践建议

本篇中主要描述了⼏种常⻅的拆分⽅式，并着重介绍了垂直分库带来的⼀些问题和解决思路。读者朋 友可能还有些问题和疑惑。

- 1. 我们⽬前的数据库是否需要进⾏垂直分库？ 根据系统架构和公司实际情况来，如果你们的系统还是个简单的单体应⽤，并且没有什么访问量和 数据量，那就别着急折腾“垂直分库”了，否则没有任何收益，也很难有好结果。 切记，“过度设计”和“过早优化”是很多架构师和技术⼈员常犯的⽑病。

- 2. 垂直拆分有没有原则或者技巧？


没有什么⻩⾦法则和标准答案。⼀般是参考系统的业务模块拆分来进⾏数据库的拆分。⽐如“⽤户 服务”，对应的可能就是“⽤户数据库”。但是也不⼀定严格⼀⼀对应。有些情况下，数据库拆分的粒 度可能会⽐系统拆分的粒度更粗。笔者也确实⻅过有些系统中的某些表原本应该放A库中的，却放 在了B库中。有些库和表原本是可以合并的，却单独保存着。还有些表，看起来放在A库中也OK， 放在B库中也合理。 如何设计和权衡，这个就看实际情况和架构师/开发⼈员的⽔平了。

- 3. 上⾯举例的都太简单了，我们的后台报表系统中join的表都有n个了， 分库后该怎么查？


有很多朋友跟我提过类似的问题。其实互联⽹的业务系统中，本来就应该尽量避免join的，如果有 多个join的，要么是设计不合理，要么是技术选型有误。请⾃⾏科普下OLAP和OLTP，报表类的系 统在传统BI时代都是通过OLAP数据仓库去实现的（现在则更多是借助离线分析、流式计算等⼿段 实现），⽽不该向上⾯描述的那样直接在业务库中执⾏⼤量join和统计。
