# 概述

HTP是⼀个“⽆状态”协议，这意味着Web应⽤程序服务器在响应客户端请求时不会将多个请求链接到 任何⼀个客户端。然⽽，许多Web应⽤程序的安全和正常运⾏都取决于系统能够区分⽤户并识别⽤户 及其权限。

这就需要⼀些机制来为⼀个HTP请求提供状态。它们使站点能够在会话期间对各⽤户做出适当的响 应，从⽽保持跟踪⽤户在应⽤程序中的活动（请求和响应）。

基于token的验证是⽆状态的，这也许是它相对cokie来说最⼤的优点。后端服务不需要记录token。 每个令牌都是独⽴的，包括检查其有效性所需的所有数据，并通过声明传达⽤户信息。

服务器唯⼀的⼯作就是在成功的登陆请求上签署token，并验证传⼊的token是否有效。

## JWT⼯作流程

在身份验证过程中，⼀旦⽤户使⽤其凭据成功登陆，服务器将返回JWT，该JWT必须在客户端本地保 存。这和服务器创建会话并返回cokie的传统⽅法不同。

每次⽤户要请求受保护的资源时，必须在请求中带上JWT。通常在Authorization头Bearer中，如下：

这是⼀种⽆状态的认证机制，因为⽤户状态永远不会保存在服务器内存中。服务器的受保护路由将在 授权头中检查有效的JWT，如果存在，则允许⽤户访问受保护的资源。由于JWT是⾃说明的，包含了 所有必要的信息，这就减少了多次查询数据库的需要。

这样可以完全依赖⽆状态的数据API，甚⾄可以向下游服务发出请求。API的作⽤域并不重要，因此跨 源资源共享（CORS）不会是⼀个问题，因为它不使⽤Cokie。

## 使⽤JWT的理由

现在来谈谈JWT与简单⽹⻚令牌（SWT）和安全断⾔标记语⾔令牌（SAML）相⽐的优势。

由于JSON⽐XML更短⼩，编码时其⼤⼩也较⼩，使得JWT⽐SAML更紧凑。这使得JWT成为在HTML 和HTP环境中能更快地传递。

从安全⻆度来说，SWT只能通过使⽤HMAC算法的共享密钥进⾏对称签名。但是，JWT和SAML令牌可 以以X.509证书的形式使⽤公钥/私钥对进⾏签名。与简单的JSON签名相⽐，使⽤XML数字签名签名 XML⽽不引⼊模糊的安全漏洞是⾮常困难的。

JSON解析器在⼤多数编程语⾔中很常⻅，因为它们直接映射到对象。相反，XML没有⾃然的⽂档对对 象映射。这使得使⽤JWT⽐SAML断⾔更容易。

从使⽤平台来说，JWT在Internet规模上使⽤。这突出了客户端处理多个平台上特别是移动平台上的 JSON Web令牌的便利性。
