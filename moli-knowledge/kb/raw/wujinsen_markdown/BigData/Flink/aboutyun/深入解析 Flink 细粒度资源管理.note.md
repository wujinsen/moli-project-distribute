# ⼀、细粒度资源管理与适⽤场景

在 Flink1.14 之前，使⽤的是⼀种粗粒度的资源管理⽅式，每个算⼦ slot request 所需要的资源都是未 知的，在 Flink 内部⽤⼀个 UNKNOWN 的特殊值来表示，这个值可以和任意资源规格的物理 slot 来匹 配。从 TaskManager (以下简称 TM) 的⻆度来说，它拥有的 slot 个数和每个 slot 的资源维度都是根据 Flink 配置静态决定的。

对于多数简单作业，现有的粗粒度资源管理已经可以基本满⾜对资源效率的要求。⽐如上图作业，由 Kafka 读⼊数据后经过⼀些简单的处理，最终将数据写⼊到 Redis 中。对于这种作业，我们很容易将上 下游并发保持⼀致，并将作业的整个 pipeline 放到⼀个 SlotSharingGroup (以下简称 SG) 中。这种情 况下，slot 的资源需求是基本相同的，⽤户直接调整默认的slot配置即可达到很⾼的资源利⽤效率，同 时由于不同的 task 热点峰值不⼀定相同，通过削峰填⾕效应，将不同的 task 放到⼀个⼤的 slot ⾥， 还可以进⼀步降低整体的资源开销。

然⽽对于⼀些⽣产中可能遇到的复杂作业，粗粒度资源管理并不能很好地满⾜他们的需求。

⽐如图上作业，有两个 128 并发的 Kafka source 和⼀个 32 并发的 Redis 维表，上下两路数据处理路 径。⼀条是两个 Kafka source，经过 join 以后再经过⼀些聚合操作，最终将数据 sink 到第三个 16 并 发的 Kafka 中；另⼀条路径则是 Kafka 和 Redis 维表进⾏ join，结果流⼊⼀个基于 TensorFlow 的在线 推断模块，最终储存到 Reids 中。

在这个作业中粗粒度资源管理就可能导致资源利⽤效率降低。

⾸先作业上下游并发不⼀致，如果想把整个作业放到⼀个 slot 中，只能和最⾼的 128 并发对⻬，对⻬ 的过程对于轻量级的算⼦没有太⼤问题，但是对于⽐较重的资源消耗的算⼦，会导致很⼤的资源浪 费。⽐如图上的 Redis 维表，它将所有数据都缓存到内存中来提⾼性能，⽽聚合算⼦则需要⽐较⼤的 managed memory 来存储 state。对于这两个算⼦，本来只需要分别申请 32 和 16 份资源，对⻬并发 以后则分别需要申请 128 份。

同时，整个作业的 pipeline 可能由于资源过⼤⽽⽆法放到⼀个 slot 或是 TM 中，⽐如上述算⼦的内 存，再⽐如 Tensorflow 模块需要 GPU 来保证计算效率。由于 GPU 是⼀种⾮常昂贵的资源，集群上不 ⼀定有⾜够的数量，从⽽导致作业因为对⻬并发⽽⽆法申请到⾜够的资源，最终⽆法执⾏。

我们可以将整个作业拆分成多个 SG。如图所示，我们将算⼦按照并发划分成 4 个 SG，保证每个

SG 内部的并发是对⻬的。但是由于每个 slot 只有⼀种默认规格，依然需要将该 slot 的所有资源维度 都对⻬到各个 SG 的最⼤值，⽐如内存需要和 Redis 维表的需求对⻬，managed memory 需要和聚 合算⼦对⻬，甚⾄扩展资源中都需要加⼊⼀块 GPU，这依然不能解决资源浪费的问题。

为了解决这个问题，我们提出了细粒度资源管理，其基本思想是，每个 slot 的资源规格都可以单独定 制，⽤户按需申请，最⼤化资源的利⽤效率。

综上，细粒度资源管理就是通过使作业各个模块按需申请和使⽤资源来提⾼资源的整体利⽤效率。它 的适⽤场景包括以下⼏种：作业中上下游 task 并发有显著差异、pipeline 的资源过⼤或者其中包含⽐ 较昂贵的扩展资源。这⼏种情况都需要将作业拆分成多个 SG，⽽不同的 SG 资源需求存在差异，这 时通过细粒度资源管理就能减少资源浪费。此外，对于批任务，作业可能包含⼀个或多个 stage，不同 stage 之间资源消耗存在显著差异，同样需要细粒度资源管理来减少资源开销。

# ⼆、Flink资源调度框架

Flink 的资源调度框架中主要有三个⻆⾊，分别是 JobMaster (以下简称 JM)，ResourceManager (以 下简称 RM) 和 TaskManager。⽤户写好的任务⾸先会被编译成 JobGraph，注⼊资源后提交到 JM， JM 的作⽤就是管理 JobGraph 的资源申请以及执⾏部署。

JM 中的调度相关的组件是 Scheduler，它会根据 JobGraph ⽣成⼀系列 SlotRequest，然后将这些 SlotRequest 进⾏聚合，⽣成⼀个 ResourceRequirement 发送给 RM，RM 接到资源声明以后，⾸先会 检查集群中现有的资源能否满⾜其需求，可以的话就会向 TM 发出请求，让他给对应的 JM 去 ofer slot (这⾥ slot 的分配由 SlotManager 组件来完成)。如果现有资源不够，它会通过内部的 driver 向外 部的 K8s 或者 Yarn 申请新的资源，最终 JM 接收⾜够多的 slot 之后就会开始部署算⼦，作业才能运 ⾏起来。

顺着这个框架，接下来对细粒度资源管理中的技术实现细节和 design choice 进⾏分析阐述。

# 三、基于 SlotSharingGroup的资源配置接⼝

在⼊⼝处 Flink 需要将资源配置注⼊ JobGraph 中。这部分是 FLIP-156 中提出的基于 SlotSharingGroup 的资源配置接⼝，关于资源配置接⼝的设计选择，主要问题是资源配置的粒度：

⾸先是最⼩的算⼦粒度 operator。如果⽤户在 operator 上配置资源的话，Filnk 需要根据 chaining 和 slot sharing 进⼀步将资源聚合成 slot 级别再进⾏资源调度。

使⽤这个粒度的好处是，我们可以将资源配置与 chaining 和 slot sharing 的逻辑解耦，⽤户只需要考 虑当前算⼦的需求，⽽⽆须考虑它是否和其他算⼦嵌在⼀起或者是否调度到⼀个 slot 中。其次，它使 Flink 可以更准确地计算每个slot的资源。假如某⼀个 SG 中上下游算⼦拥有不同的并发，那么可能

SG 对应的物理 slot 需要的资源也是有差异的；⽽如果 Flink 掌握了每个算⼦的资源，它就有机会进 ⼀步优化资源效率。

当然它也存在⼀些缺点，⾸先是⽤户配置成本过⾼，⽣产中的复杂作业包含了⼤量算⼦，⽤户很难⼀ ⼀配置。其次，这种情况下，很难⽀持粗细粒度混合资源配置。⼀个 SG 中如果既存在粗粒度，⼜存 在细粒度的算⼦，会导致 Flink ⽆法判断其所需要的资源到底是多少。最后，由于⽤户对资源的配置或 估计会存在⼀定程度的偏差，这种偏差会不断累积，算⼦的削峰填⾕效应也⽆法被有效利⽤。

第⼆种选择是将算⼦ chaining 后形成的 task 作为资源配置的粒度。这种情况下，我们必须向⽤户暴露 Flink 内部的 chaining 逻辑，同时 Flink 的 runtime 依然需要根据 task 的 slot sharing 的配置进⼀步将 资源聚合成 slot 级别再进⾏资源调度。

它的优缺点和算⼦粒度⼤致⼀样，只不过相⽐算⼦，它在⽤户的配置成本上有了⼀定程度的降低，但 这依然是⼀个痛点。同时它的代价是⽆法将资源配置和 chaining 解耦，将 chaining 和 Flink 内部的逻 辑暴露给⽤户，导致内部潜在的优化受到限制。因为⼀旦⽤户配置了某个 task 的资源，chaining 逻辑 的改变可能让 task 分裂成两个或者三个，造成⽤户配置不兼容。

第三种选择是直接将 SlotSharingGroup 作为资源配置的粒度，这样对 Flink 来说资源配置所⻅既所 得，省略了前⾯的资源聚合逻辑。

同时这种选择还有以下⼏个优点：

第⼀，使⽤户的配置更灵活。我们将配置粒度的选择权交给⽤户，既可以配置算⼦的资源，也可以配 置 task 资源，甚⾄配置⼦图的资源，只需要将⼦图放到⼀个 SG ⾥然后配置它的资源即可。

第⼆，可以较为简单地⽀持粗细粒度混合配置。所有配置的粒度都是 slot，不⽤担⼼同⼀个 slot 中既 包含粗粒度⼜包含细粒度的 task。对于粗粒度的 slot，可以简单地按照 TM 默认的规格计算它的资源 ⼤⼩，这个特性也使得细粒度资源管理的分配逻辑可以兼容粗粒度调度的，我们可以把粗粒度看作是 细粒度的⼀种特例。

第三，它使得⽤户可以利⽤不同算⼦之间的削峰填⾕效应，有效减少偏差产⽣的影响。

当然，也会引⼊⼀些限制，它将资源配置的 chaining 以及 Slot Sharing 耦合在了⼀起。此外如果⼀个 SG ⾥算⼦存在并发差异，那么为了最⼤化资源利⽤效率，可能需要⽤户⼿动拆组。

综合考虑，我们在 FLIP-156 中，最终选择了基于 SlotSharingGroup 的资源配置接⼝。除了上述提到 的优点，最重要的是从资源调度框架中可以发现，slot 实际上就是资源调度中最基本的单位，从 Scheduler 到 RM\TM 都是以 slot 为单位进⾏资源调度申请的，直接使⽤这个粒度，避免了增加系统的 复杂度。

回到示例作业，在⽀持了细粒度资源管理配置接⼝后，我们就可以为 4 个 SG 配置不同的资源，如上 图所示。只要调度框架严格按照这个原则进⾏匹配，我们就可以最⼤化资源利⽤效率。

# 四、动态资源切割机制

解决了资源配置以后，下⼀步就是为这些资源申请 slot，这⼀步需要⽤到 FLIP-56 提出的动态资源切 割机制。

简单回顾⼀下这幅图，现在最左侧的 JobGraph 已经有资源了，往右⾛就进⼊了 JM、RM 和 TM 的资 源调度。在粗粒度资源管理下，TM 的 slot 都是固定⼤⼩、根据启动配置来决定的，RM 在这种情况没 法满⾜不同规格的 slot 请求的，因此我们需要对 slot 的创建⽅式进⾏⼀定的改造。

先来看现有的静态 slot 申请机制。实际上 TM 启动的时候 slot 就已经划分好了，并且标记了编号。它 会将这些 slot 上报给 Slot Manager，slot request 来临时 Slot Manager 会决定申请 slot1、slot3，最 后 slot1 上的 task 运⾏完以后会释放 slot。这种情况下，只有 slot3 处于占⽤的状态。我们可以发现， 这时虽然 TM 有 0.75 core，3G 的空闲资源，但如果 job 去申请对应资源⼤⼩的 slot，TM 也⽆法满⾜ 它，因为 slot 已经提前划分好了。

因此我们提出了动态资源切割机制。slot 不再是 TM 启动后就⽣成并且不变的，⽽是根据实际 slot 的 请求动态地从 TM 上切割下来。TM 启动时，我们把能分配给 slot 的资源看作是⼀整个资源池，⽐如 上图有 1core，4G 内存的资源，现在有⼀个细粒度的作业，Slot Manager 决定从 TM 上要⼀个 0.25core，1G 的 slot，TM 会检查⾃⼰的资源池是否能够切下这个 slot，然后动态⽣成 slot 并分配对 应的资源给 JM，接下来这个作业⼜申请⼀个 0.5core，2G 的 slot，Slot Manager 还是可以从同⼀个 TM 上申请 slot，只要不超过空闲资源就可以。当某个 slot 不再需要时，我们可以将它销毁，对应的资 源会回到空闲资源池。

通过这种机制，我们解决了细粒度资源请求如何满⾜的问题。

回到示例作业，我们只需要起 8 个同样规格的 TM 就能调度作业，每个 TM 上带⼀块 GPU 来满⾜

SG4，之后将 CPU 密集型的 SG1 和内存密集型的 SG2 和 SG3 进⾏混布，对⻬ TM 上整体的 CPU 内存⽐即可。

# 五、资源申请策略

何谓资源申请策略？它包含 RM 与 Resource Provider 还有 TM 交互时的两个决策，⼀个是从 Resource Provider 处申请什么资源规格的 TM 以及各个规格 TM 各需要⼏个，另⼀个是如何将 slot 摆 放到各个 TM 中。实际上这两个决策都是在 Slot Manager 组件内部进⾏的。

粗粒度的资源申请策略⽐较简单，因为只存在⼀种规格的 TM，并且 slot 规格都是⼀样的。在分配策 略上只需要考虑是否将 slot 尽量平铺到各个 TM。但在细粒度资源管理下的策略就需要考虑到不同的 需求。

⾸先我们引⼊了动态资源切割机制。slot 的调度就可以看作⼀个多维装箱问题，既需要考虑如何减少 资源碎⽚，也需要保障资源调度效率。此外还有 slot 是否需要评估，以及集群可能对 TM 的资源规格 有⼀些要求，⽐如不能过⼩，在 K8s 上如果 TM 资源过⼩，会导致启动过慢，最后注册超时，但也不 能太⼤，会影响 K8s 的调度效率。

⾯对上述复杂性，我们将这个资源申请策略抽象出来，定义了⼀个 ResourceAlocationStrategy，Slot Manager 会将当前的资源请求和集群中现有的可⽤资源告诉 strategy，strategy 负责决策并告诉 Slot Manager 现有资源如何分配、还需要申请多少个新的 TM 以及它们分别的规格，还有是否存在⽆法满 ⾜的作业。

⽬前细粒度资源管理还处于 beta 版本，社区内置了⼀个简单的默认资源管理策略。在这个策略下 TM 的规格是固定的、根据粗粒度的配置决定的，如果某个 slot 的请求⼤于资源配置，可能导致⽆法分 配，这是它的局限性。在资源分配⽅⾯，它会顺序扫描当前空闲的 TM，只要满⾜ slot 的请求就会直 接切割，这种策略保障了资源调度即使在⼤规模的任务上也不会成为瓶颈，但代价是⽆法避免资源碎 ⽚的产⽣。

# 六、总结与未来展望

细粒度资源管理⽬前在 Flink 中还只是 beta 版本。上图可以看到，对于 runtime 来说，通过 FLIP-56 与 FLIP-156，细粒度资源管理的⼯作已经基本完成了。⽽从⽤户接⼝的⻆度，FLIP-169 已经开放了 Datastream API 上的细粒度配置，具体如何配置，可以参考社区的⽤户⽂档。

未来，我们的发展⽅向主要是以下⼏个⽅⾯：

第⼀，定制更多的资源管理策略来满⾜不同场景，⽐如 sesion 和 OLAP 等；

第⼆，⽬前我们是把扩展资源看作⼀个 TM 级别的资源，TM 上的每个 slot 都可以看到它的信息，之 后我们会对它的 scope 进⾏进⼀步限制；

第三，⽬前细粒度资源管理可以⽀持粗细粒度混合配置，但是存在⼀些资源效率上的问题，⽐如粗粒 度的 slot 请求可以被任意⼤⼩的 slot 满⾜，未来我们会进⼀步优化匹配逻辑，更好地⽀持混合配置；

第四，我们会考虑适配社区新提出的 Reactive Mode；

最后，对 WebUI 进⾏优化，能够展示 slot 的切分信息等。
