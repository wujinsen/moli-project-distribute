跳数索引

影响ClickHouse查询性能的因素很多。在⼤多数场景中，关键因素是ClickHouse在计算查询WHERE⼦ 句条件时是否可以使⽤主键。因此，选择适⽤于最常⻅查询模式的主键对于表的设计⾄关重要。 然⽽，⽆论如何仔细地调优主键，不可避免地会出现不能有效使⽤它的查询⽤例。⽤户通常依赖于 ClickHouse获得时间序列类型的数据，但他们通常希望根据其他业务维度(如客户id、⽹站URL或产品 编号)分析同⼀批数据。在这种情况下，查询性能可能会相当差，因为应⽤WHERE⼦句条件可能需要对 每个列值进⾏完整扫描。虽然ClickHouse在这些情况下仍然相对较快，但计算数百万或数⼗亿个单独 的值将导致“⾮索引”查询的执⾏速度⽐基于主键的查询慢得多。 在传统的关系数据库中，解决这个问题的⼀种⽅法是将⼀个或多个“⼆级”索引附加到表上。这是⼀个 b-树结构，允许数据库在O(log(n)时间内找到磁盘上所有匹配的⾏，⽽不是O(n)时间(⼀次表扫描)， 其中n是⾏数。但是，这种类型的⼆级索引不适⽤于ClickHouse(或其他⾯向列的数据库)，因为磁盘上 没有单独的⾏可以添加到索引中。 相反，ClickHouse提供了⼀种不同类型的索引，在特定情况下可以显著提⾼查询速度。这些结构被标 记为跳数索引，因为它们使ClickHouse能够跳过保证没有匹配值的数据块。

基本操作

⽤户只能在MergeTre表引擎上使⽤数据跳数索引。每个跳数索引都有四个主要参数：

索引名称。索引名⽤于在每个分区中创建索引⽂件。此外，在删除或具体化索引时需要将其作为参 数。

索引的表达式。索引表达式⽤于计算存储在索引中的值集。它可以是列、简单操作符、函数的⼦集 的组合。

类型。索引的类型控制计算，该计算决定是否可以跳过读取和计算每个索引块。

GRANULARITY。每个索引块由颗粒（granule）组成。例如，如果主表索引粒度为8192⾏， GRANULARITY为4，则每个索引“块”将为32768⾏。

当⽤户创建数据跳数索引时，表的每个数据部分⽬录中将有两个额外的⽂件。

skpidx{index_name}.idx：包含排序的表达式值。

skpidx{index_name}.mrk2：包含关联数据列⽂件中的相应偏移量。

如果在执⾏查询并读取相关列⽂件时，WHERE⼦句过滤条件的某些部分与跳数索引表达式匹配， ClickHouse将使⽤索引⽂件数据来确定每个相关的数据块是必须被处理还是可以被绕过(假设块还没有 通过应⽤主键索引被排除)。这⾥⽤⼀个⾮常简单的示例：考虑以下加载了可预测数据的表。

# 跳数索引类型

minmax

这种轻量级索引类型不需要参数。它存储每个块的索引表达式的最⼩值和最⼤值(如果表达式是⼀个元 组，它分别存储元组元素的每个成员的值)。对于倾向于按值松散排序的列，这种类型⾮常理想。在查 询处理期间，这种索引类型的开销通常是最⼩的。 这种类型的索引只适⽤于标量或元组表达式⸺索引永远不适⽤于返回数组或map数据类型的表达式。

set

这种轻量级索引类型接受单个参数max_size，即每个块的值集(0允许⽆限数量的离散值)。这个集合包 含块中的所有值(如果值的数量超过max_size则为空)。这种索引类型适⽤于每组颗粒中基数较低(本质 上是“聚集在⼀起”)但总体基数较⾼的列。 该索引的成本、性能和有效性取决于块中的基数。如果每个块包含⼤量惟⼀值，那么针对⼤型索引集 计算查询条件将⾮常昂贵，或者由于索引超过max_size⽽为空，因此索引将不应⽤。

# 跳数索引的配置

有两个可⽤的设置可应⽤于跳数索引。

use_skip_indexes (0或1，默认为1)。不是所有查询都可以有效地使⽤跳过索引。如果⼀个特定的过 滤条件可能包含很多颗粒，那么应⽤数据跳过索引将导致不必要的、有时甚⾄是⾮常⼤的成本。对 于不太可能从任何跳过索引中获益的查询，将该值设置为0。

force_data_ski ping_indexes (以逗号分隔的索引名列表)。此设置可⽤于防⽌某些类型的低效查 询。在某些情况下，除⾮使⽤跳过索引，否则查询表的开销太⼤，如果将此设置与⼀个或多个索引 名⼀起使⽤，则对于任何没有使⽤所列索引的查询将返回⼀个异常。这将防⽌编写糟糕的查询消耗 服务器资源。
