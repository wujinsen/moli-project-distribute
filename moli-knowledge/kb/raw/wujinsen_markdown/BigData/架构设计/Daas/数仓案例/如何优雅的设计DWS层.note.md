对于数仓的分层，⼤家最⽿熟能详的就是基于OneData⽅法论的三层数仓划分，分别是：数据引⼊层 （ODS，Operational Data Store）、数据公共层（CDM，Comon Dimenions Model）和数据应⽤层 （ADS，Aplication Data Store）。 当然，涉及到每⼀层具体该怎么建模，可能⼤家都有⾃⼰的理解。数据建模⽆疑是重中之重，如果我 们把指标⽐作树上的果实，那么模型就好⽐是⼤树的躯⼲，想让果实结得好，必须让树⼲变得粗壮。

我们先来回想下，构建数据中台的初衷是什么： 没有可以复⽤的数据， ⼤家不得不使⽤原始数据进⾏清洗、加⼯和计算指标… 这根源就在于数据模型的⽆法复⽤，数据开发都是烟囱式的。所以要解决这个问题，就要搞清楚健壮 的数据模型该如何设计。

数据引⼊层（ODS，Operational Data Store，⼜称数据基础层）：将原始数据⼏乎⽆处理地存放在 数据仓库系统中，结构上与源系统基本保持⼀致，是数据仓库的数据准备区。这⼀层的主要职责是 将基础数据同步、存储。

数据公共层（CDM，Comon Dimenions Model）：存放明细事实数据、维表数据及公共指标汇总 数据。其中，明细事实数据、维表数据⼀般根据ODS层数据加⼯⽣成。公共指标汇总数据⼀般根据 维表数据和明细事实数据加⼯⽣成。CDM层⼜细分为维度层（DIM）、明细数据层（DWD）和汇总 数据层（DWS），采⽤维度模型⽅法作为理论基础， 可以定义维度模型主键与事实模型中外键关 系，减少数据冗余，也提⾼明细数据表的易⽤性。在汇总数据层同样可以关联复⽤统计粒度中的维 度，采取更多的宽表化⼿段构建公共指标数据层，提升公共指标的复⽤性，减少重复加⼯。

维度层（DIM，Dimension）：以维度作为建模驱动，基于每个维度的业务含义，通过添加维度属 性、关联维度等定义计算逻辑，完成属性定义的过程并建⽴⼀致的数据分析维表。为了避免在维度 模型中冗余关联维度的属性，基于雪花模型构建维度表。

明细数据层（DWD，Data Warehouse Detail）：以业务过程作为建模驱动，基于每个具体的业务 过程特点，构建最细粒度的明细事实表。可将某些重要属性字段做适当冗余，也即宽表化处理。

汇总数据层（DWS，Data Warehouse Sumary）：以分析的主题对象作为建模驱动，基于上层的 应⽤和产品的指标需求，构建公共粒度的汇总指标表。以宽表化⼿段物理化模型，构建命名规范、 ⼝径⼀致的统计指标，为上层提供公共指标，建⽴汇总宽表、明细事实表。

数据应⽤层（ADS，Aplication Data Store）：存放数据产品个性化的统计指标数据，根据CDM层 与ODS层加⼯⽣成。

DWS层很重要？ 通常，⼤家都会有这样的疑问：明明可以直接从DWD层取数，为什么要多此⼀举建⽴DWS的汇总逻辑 表呢？

我想说的是：如果在业务场景不复杂的情况下，那样做是没有问题的。可⼀旦⾯对复杂的业务场景， 那这种做法⽆疑是混乱的根源所在，前⾯提到的烟囱式开发、计算资源的浪费等等情况，正是这样产 ⽣的。

我们需要的是从数据明细层中做⼀个初步的汇总，抽象出来⼀些通⽤的维度：时间、⽤户ID、IP等，并 根据这些维度做⼀些统计，⽐如⽤户每个时间段在不同登录IP购买的商品数等。

这⾥做⼀层轻度的汇总会让计算更加的⾼效，在此基础上如果计算仅7天、30天、90天的⾏为的话会 快很多。我们希望80%的业务都能通过我们的DWS层计算，⽽不是ODS或者DWD。

应该遵循的设计原则 聚集是指针对原始明细粒度的数据进⾏汇总。DWS汇总数据层是⾯向分析对象的主题聚集建模，以零 售的场景为例，我们最终的分析⽬标为：最近⼀天某个类⽬（例如，厨具）商品在各省的销售总额、 该类⽬销售额Top10的商品名称、各省⽤户购买⼒分布。

因此，我们可以以最终交易成功的商品、类⽬、买家等⻆度对最近⼀天的数据进⾏汇总。数据聚集的 注意事项如下：

聚集是不跨越事实的。聚集是针对原始星形模型进⾏的汇总。为获取和查询与原始模型⼀致的结 果，聚集的维度和度量必须与原始模型保持⼀致，因此聚集是不跨越事实的，所以原⼦指标只能基 于⼀张事实表定义，但是⽀持原⼦指标组合为衍⽣原⼦指标。

聚集会带来查询性能的提升，但聚集也会增加ETL维护的难度。当⼦类⽬对应的⼀级类⽬发⽣变更 时，先前存在的、已经被汇总到聚集表中的数据需要被重新调整。

此外，进⾏DWS层设计时还需遵循数据公⽤性原则。数据公⽤性需要考虑汇总的聚集是否可以提供给 第三⽅使⽤。我们可以思考基于某个维度的聚集是否经常⽤于数据分析中，如果答案是肯定的，就有 必要把明细数据经过汇总沉淀到聚集表中。

简单的说就是： 主题 宽表 轻度汇总

思考：如何设计出完美的DWS层？ 在我们数据中台实际实施落地的过程中，团队不但要建设公共数据层，形成数据中台，还要承担着新 需求的压⼒。

往往我们要先满⾜需求（活下去），再研发公共数据层（构建美好未来），在满⾜业务需求的过程 中，再根据需求不断对模型进⾏迭代和优化，随着时间的推移，越来越多的业务需求可以通过DWS层 的数据完成。

这⼀过程中，完善度是很好的考核标准，主要看DWS层汇总的数据能满⾜多少的查询需求，如果汇总 数据⽆法满⾜需求，使⽤数据的⼈就必须使⽤明细的数据，甚⾄是ODS层的原始数据。

# DWS/ADS层的完善度越⾼，说明数据的上层建设越完善，⽽从使⽤者的⻆度来说，查询快、易取数、 ⽤的爽，那才是硬道理。
