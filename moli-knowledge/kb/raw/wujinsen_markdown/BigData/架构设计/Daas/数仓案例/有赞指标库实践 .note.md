值键：有些情况维度表在事实表上会有值键的冗余，这种情况下事实表可以不需要和维度表做 join 就能取出维度信息。在事实表上有0-1个。

- 2.3.1 关联表 原⼦指标需要关联到具体的事实表和字段。如上图配置了数仓统⼀中间层 DW 层的4张表。这意味着当 前这个指标的数据可以从这4张表⾥取。为什么会有4张表⽽不是1张表？因为这4张表可能是不同维度 的，适⽤于不同维度情况下的当前指标的取数。原⼦指标关联事实表只需要指定事实表上的指标字段 即可。每张事实表都是等价的，不需要设置主表。
- 2.3.2 聚合⽅式 聚合⽅式描述的是当前事实表上的指标如果需要做聚合运算，可以使⽤的聚合⽅式。默认聚合⽅式就 是按维度做聚合的时候如果没有指定聚合⽅式时采⽤的聚合函数。⽐如数仓中间层表提供的表⾥有店 铺，⽤户，⽀付⾦额3个字段。如果业务需要看店铺维度下的⽀付⾦额。那就需要对店铺做 group by ，对⽀付⾦额做 sum。这⾥的 sum 就是配置的默认聚合⽅式。


- 2.4 修饰词管理 修饰词是维度的某⼀些特殊的值。对应 SQL 中的 where 过滤条件。⽐如业务⽅想看店铺维度下的 weapp 的⽀付⾦额。制作出来的表结构可能是如下图这样的结构。 weapp 可能只是渠道下某⼀个值。因为业务⽅的需求仅仅只是查看 weapp 渠道，不需要查看其他⽐如 H5， web 等渠道，所以表结构可以没有渠道这个维度，⽽把 weapp 修饰词直接做在事实字段上。 SQL ⼤致是这样的形式：select sum(⽀付⾦额) from table group by 店铺 where 渠道 = 'weapp' 从中我们可以看出，维度和修饰词有⼀定的相互替代的作⽤。什么时候⽤维度什么时候⽤修饰词⽬前 并没有严格的定论。只是能⽤维度来解决的问题尽量⽤维度，⽽不是修饰词，因为维度是⼀种更加通 ⽤的形式。业务⽅可以在⾃⼰的 mysql 库再根据⾃⼰的需要对维度做过滤。
- 2.5 派⽣指标 维度和原⼦指标更多的是站在数仓和 BI 的⻆⻆度设计的，符合数仓的星型模型。每张事实表上存在多 个指标，每张事实表含有多张维度表的外键。但是业务⽅更关⼼的指标，是有实际业务含义，可以直 接取数据的指标。⽐如店铺近1天订单⽀付⾦额就是⼀个派⽣指标，会被直接在产品上展示给商家看。


但是这个指标却不能直接从数仓的统⼀中间层⾥取数（因为没有现成的事实字段，数仓提供的⼀般都 是⼤宽表）。需要有⼀个桥梁连接数仓中间层和业务⽅的指标需求，于是便有了派⽣指标。 从上述的例⼦中可以看出派⽣指标=维度+原⼦指标+修饰词。当维度，原⼦指标，修饰词都确定的时候 就可以唯⼀确定⼀个派⽣指标，同时给出具体数值。店铺近1天订单⽀付⾦额中店铺是维度，近1天是 ⼀个时间类型的修饰词，⽀付⾦额是⼀个原⼦指标。业务⽅制作每⼀个派⽣指标都是通过选择维度， 原⼦指标，修饰词三种元数据来定义的，相对于使⽤名称来区别不同指标，更可以保证指标的唯⼀ 性。如果2个派⽣指标是不同的，那他们的组成部分⼀定会有区别，或是不同维度，或是不同原⼦指 标，修饰词。
