为什么要构建实时数据仓库

传统的离线数据仓库将业务数据集中进⾏存储后，以固定的计算逻辑定时进⾏ETL和其它建模后产出报表等应⽤。离线数据仓 库主要是构建T+1的离线数据，通过定时任务每天拉取增量数据，然后创建各个业务相关的主题维度数据，对外提供T+1的数 据查询接⼝。计算和数据的实时性均较差，业务⼈员⽆法根据⾃⼰的即时性需要获取⼏分钟之前的实时数据。数据本身的价值 随着时间的流逝会逐步减弱，因此数据发⽣后必须尽快的达到⽤户的⼿中，实时数仓的构建需求也应运⽽⽣。 总之就是⼀句话：时效性的要求。

美团的实时数仓设计

![image 8](<你需要的不是实时数仓 你需要的是一款合适且强大的OLAP数据库(上).note_images/imageFile8.png>)

美团实时数仓数据分层架构 美团的技术⽅案由以下四层构成：

ODS 层：Binlog 和流量⽇志以及各业务实时队列。

数据明细层：业务领域整合提取事实数据，离线全量和实时变化数据构建实时维度数据。

数据汇总层：使⽤宽表模型对明细数据补充维度数据，对共性指标进⾏汇总。

App 层：为了具体需求⽽构建的应⽤层，通过 RPC 框架对外提供服务。

根据不同业务场景，实时数仓各个模型层次使⽤的存储⽅案和OLAP引擎如下：

数据明细层 对于维度数据部分场景下关联的频率可达 10w+ TPS，我们选择 Cellar（美团内部分布式K-V存储系统，类 似Redis） 作为存储，封装维度服务为实时数仓提供维度数据。

数据汇总层 对于通⽤的汇总指标，需要进⾏历史数据关联的数据，采⽤和维度数据⼀样的⽅案通过 Cellar 作为存储，⽤ 服务的⽅式进⾏关联操作。

数据应⽤层 应⽤层设计相对复杂，再对⽐了⼏种不同存储⽅案后。我们制定了以数据读写频率 1000 QPS 为分界的判断 依据。对于读写平均频率⾼于 1000 QPS 但查询不太复杂的实时应⽤，⽐如商户实时的经营数据。采⽤ Cellar 为存储， 提供实时数据服务。对于⼀些查询复杂的和需要明细列表的应⽤，使⽤ Elasticsearch 作为存储则更为合适。⽽⼀些查询 频率低，⽐如⼀些内部运营的数据。 Druid 通过实时处理消息构建索引，并通过预聚合可以快速的提供实时数据 OLAP 分 析功能。对于⼀些历史版本的数据产品进⾏实时化改造时，也可以使⽤ MySQL 存储便于产品迭代。

总之，在OLAP选型上同样以Druid为主。

⽹易严选的实时数仓整体框架依据数据的流向分为不同的层次，接⼊层会依据各种数据接⼊⼯具 收集各个业务系统的数据。 消息队列的数据既是离线数仓的原始数据，也是实时计算的原始数据，这样可以保证实时和离线的原始数据是统⼀的。 在计 算层经过 Flink+实时计算引擎做⼀些加⼯处理，然后落地到存储层中不同存储介质当中。不同的存储介质是依据不同的应⽤ 场景来选择。框架中还有Flink和Kafka的交互，在数据上进⾏⼀个分层设计，计算引擎从Kafka中捞取数据做⼀些加⼯然后放 回Kafka。在存储层加⼯好的数据会通过服务层的两个服务：统⼀查询、指标管理，统⼀查询是通过业务⽅调取数据接⼝的⼀ 个服务，指标管理是对数据指标的定义和管理⼯作。通过服务层应⽤到不同的数据应⽤，数据应⽤可能是我们的正式产品或者 直接的业务系统。 基于以上的设计，技术选型如下：

对于存储层会依据不同的数据层的特点选择不同的存储介质，ODS层和DWD层都是存储的⼀些实时数据，选择的是Kafka进 ⾏存储，在DWD层会关联⼀些历史明细数据，会将其放到 Redis ⾥⾯。在DIM层主要做⼀些⾼并发维度的查询关联，⼀般将 其存放在HBase⾥⾯，对于DIM层⽐价复杂，需要综合考虑对于数据落地的要求以及具体的查询引擎来选择不同的存储⽅式。 对于常⻅的指标汇总模型直接放在 MySQL ⾥⾯，维度⽐较多的、写⼊更新⽐较⼤的模型会放在HBase⾥⾯，还有明细数据 需要做⼀些多维分析或者关联会将其存储在Greenplum⾥⾯，还有⼀种是维度⽐较多、需要做排序、查询要求⽐较⾼的，如 活动期间⽤户的销售列表等⼤列表直接存储在Redis⾥⾯。 ⽹易严选选择了GreenPulm、Hbase、Redis和MySQL作为数据的计算和透出层。 GreenPulm的技术特点如下：

⽀持海量数据存储和处理

⽀持Just In Time BI：通过准实时、实时的数据加载⽅式，实现数据仓库的实时更新，进⽽实现动态数据仓库 （ADW），基于动态数据仓库，业务⽤户能对当前业务数据进⾏BI实时分析（Just In Time BI）

⽀持主流的sql语法，使⽤起来⼗分⽅便，学习成本低

扩展性好，⽀持多语⾔的⾃定义函数和⾃定义类型等

提供了⼤量的维护⼯具，使⽤维护起来很⽅便

⽀持线性扩展：采⽤MPP并⾏处理架构。在MPP结构中增加节点就可以线性提供系统的存储容量和处理能⼒

较好的并发⽀持及⾼可⽤性⽀持除了提供硬件级的Raid技术外，还提供数据库层Mirror机制保护，提供Master/Stand by 机制进⾏主节点容错，当主节点发⽣错误时，可以切换到Stand by节点继续服务

总结

我们通过以上的分析可以看出，在整个实时数仓的建设中，业界已经有了成熟的⽅案。整体架构设计通过分层设计为OLAP查 询分担压⼒，让出计算空间，复杂的计算统⼀在实时计算层做，避免给OLAP查询带来过⼤的压⼒。汇总计算教给OLAP数据 库进⾏。我们可以这么说，在整个架构中实时计算⼀般是Spark+Flink配合，消息队列Kafka⼀家独⼤，整个⼤数据领域消息 队列的应⽤中仍然处理垄断地位，后来者Pulsar想做出超越难度很⼤，Hbase、Redis和MySQL都在特定场景下有⼀席之 地。 唯独在OLAP领域，百家争鸣，各有所⻓。⼤数据领域开源OLAP引擎包括但是不限于Hive、Druid、Hawq、Presto、 Impala、Sparksql、Clickhouse、Greenplum等等。下⼀篇我们就各个开源OLAP引擎的优缺点和使⽤场景做出详细对 ⽐，让开发者进⾏技术选型时做到⼼中有数。
