⼀、数据倾斜调优

数据倾斜是开发画像过程中常遇到的问题，当任务执⾏⼀直卡在map 10%、reduce 9%，最后 的1%花了⼏个⼩时都没执⾏完时，这时⼀般是遇到了数据倾斜。

问题出现的原因是当进⾏分布式计算时，由于某些节点需要计算的数据较多，导致其他节点的 reduce阶段任务执⾏完成时，该节点的任务还没有执⾏完成，造成其他节点等待该节点执⾏完成的情 况。⽐如两张⼤表在join的时候⼤部分key对应10条数据，但是个别⼏个key对应了10万条数据，对应 10条数据的task很快执⾏完成了，但对应了10万数据的key则要执⾏⼏个⼩时。

下图便是⼀个典型的例⼦。

b这个key在3个节点上有 1条数据， a和 c在3个节点上分别有2条和1条数据，这些数据都会被 拉取到⼀个task上处理。处理 b这个task的运⾏时间可能是处理 a和 c的task的运⾏时间数倍，整体 运⾏速度由最慢的task决定。

下⾯介绍两种解决数据倾斜问题的⽅案。

⽅案⼀：过滤掉倾斜数据

当少量key重复次数特别多，如果这种key不是业务需要的key，可以直接过滤掉。这⾥有⼀张埋点

⽇志表 ods.page_event_log ，需要和订单表 dw.order_info_fact 做join关联。在执⾏Hive的过程中发 现任务卡在map 10%、reduce 9%，最后的1%⼀直运⾏不完。考虑应该是在join的过程中出现了数 据倾斜，下⾯进⾏排查。

⽅案⼆：引⼊随机数

数据按照类型 group by 时，会将相同的key所需的数据拉取到⼀个节点进⾏聚合，⽽当某组数据 量过⼤时，会出现其他组已经计算完成⽽当前任务未完成的情况。可以考虑加⼊随机数，将原来的⼀ 组key强制拆分为多组进⾏聚合。下⾯通过⼀个案例进⾏介绍。

在Spark执⾏“insert overwrite table表名”的语句时，由于多线程并⾏向HDFS写⼊且RD默认分区 为20个，因此默认情况下会产⽣20个⼩⽂件。

Spark中可以使⽤ reparation 或 coalesce 对RD的分区重新进⾏划分，reparation 是 coalesce 接⼝中 shufle 为true的实现。

在Spark内部会对每⼀个分区分配⼀个task 执⾏，如果task过多，那么每个task处理的数据量很 ⼩，这就会造成线程频繁在task之间切换，导致集群⼯作效率低下。为解决这个问题，常采⽤RD重 分区函数来减少分区数量，将⼩分区合并为⼤分区，从⽽提⾼集群⼯作效率。

- 36 三、缓存中间数据


Spark的⼀个重要的能⼒就是将数据持久化缓存，这样在多个操作期间都可以访问这些持久化的数 据。当持久化⼀个RD时，每个节点的其他分区都可以使⽤RD在内存中进⾏计算，在该数据上的其 他action操作将直接使⽤内存中的数据，这样会使其操作计算速度加快。对RD的复杂操作如果没有持 久化，那么⼀切的操作都会从源头开始，⼀步步往后计算，不会复⽤原始数据。

在画像标签每天ETL的时候，对于⼀些中间计算结果可以不落磁盘，只需把数据缓存在内存中。⽽ 使⽤Hive进⾏ETL时需要将⼀些中间计算结果落在临时表中，使⽤完临时表后再将其删除。

RD可以使⽤ persist 或 cache⽅法进⾏持久化，使⽤ StorageLevel 对象给 persist ⽅法设置存储 级别时，常⽤的存储级别如下所示。

MEMORY_ONLY：只存储在内存中 MEMORY_ONLY_2：只存储在内存中，每个分区在集群中两个节点上建⽴副本； DISK_ONLY：只存储在磁盘中； MEMORY_AND_DISK：先存储在内存中，内存不够的话存储在磁盘中

其中 cache ⽅法等同于调⽤ persist（）的 MEMORY_ONLY⽅法

在画像标签开发中，⼀般从Hive中读取数据，然后将需要做中间处理的DataFrame注册成缓存 表。

四、开发中间表

在⽤户画像迭代开发的过程中，初期开发完标签后，通过对标签加⼯作业的⾎缘图整理，可以找 到使⽤相同数据源的标签，对这部分标签，可以通过加⼯中间表缩减每⽇画像调度作业时间。

做中间层设计前需要明确⼏个重要的点：

- 1）这个中间层对应的业务场景、业务⽬标是什么？
- 2）业务⽅有了这份中间层数据以后可以进⾏哪些维度的分析，ETL时有了这份中间层数据可以减


少对哪些数据的重复开发计算？

- 3) 这个业务场景分析中包含哪些分析维度和指标？
- 4）同时⾯向很多业务场景的中间层不⼀定是好的中间层。

本章⼩结

之前在笔者的项⽬开发过程中，ETL调度时间过⻓是⼀个较难解决的“瓶颈”，每天的调度在跑完计 算标签、标签校验预警、计算⼈群、⼈群校验预警、同步到服务层等环节后往往需要⼏个⼩时，最后 提供到服务层数据时也⽐较晚了。在这个过程中为了减少调度时间，我们也做了很多尝试，包括对⼀ 些Hive表设计多个分区，并⾏跑任务插⼊数据；对⼀些执⾏时间过⻓的脚本进⾏调优；梳理数据⾎缘 开发中间层表，对⼀些常⻅的公共数据直接从中间层表获取数据，减少数据的重复开发计算等。在经 过多次迭代后也取得了不错的效果，将整体调度时间压缩了1/3，可以满⾜每天及时将画像数据输出到 服务层的需要。

本期介绍了画像系统在数据开发中可能遇到的需要调优的场景。通过对数据倾斜、合并⼩⽂件、 缓存中间数据、开发中间表⼏个常⻅问题的处理，可以优化ETL作业流程，减少调度的整体时间。
