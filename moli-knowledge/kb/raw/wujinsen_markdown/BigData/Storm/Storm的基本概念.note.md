## Storm记录级容错的基本原理

⾸先来看⼀下什么叫做记录级容错？storm允许⽤户在spout中发射⼀个新的源tuple时为其指定⼀ 个message id, 这个message id可以是任意的object对象。多个源tuple可以共⽤⼀个message id， 表示这多个源 tuple对⽤户来说是同⼀个消息单元。storm中记录级容错的意思是说，storm会告知 ⽤户每⼀个消息单元是否在指定时间内被完全处理了。那什么叫做完全处理呢，就是该message id绑定的源tuple及由该源tuple后续⽣成的tuple经过了topology中每⼀个应该到达的bolt的处理。举 个例⼦。在图4-1中，在spout由message 1绑定的tuple1和tuple2经过了bolt1和bolt2的处理⽣成两 个新的tuple，并最终都流向了bolt3。当这个过程完成处理完时，称message 1被完全处理了。

在storm的topology中有⼀个系统级组件，叫做acker。这个acker的任务就是追踪从spout中流出来 的每⼀个message id绑定的若⼲tuple的处理路径，如果在⽤户设置的最⼤超时时间内这些tuple没 有被完全处理，那么acker就会告知spout该消息处理失败了，相反则会告知spout该消息处理成功 了。在刚才的描述中，我们提到了”记录tuple的处理路径”，如果曾经尝试过这么做的同学可以仔 细地思考⼀下这件事的复杂程度。但是storm中却是使⽤了⼀种⾮常巧妙的⽅法做到了。在说明这 个⽅法之前，我们来复习⼀个数学定理。

- A xor A = 0.

- A xor B…xor B xor A = 0，其中每⼀个操作数出现且仅出现两次。


storm中使⽤的巧妙⽅法就是基于这个定理。具体过程是这样的：在spout中系统会为⽤户指定的 message id⽣成⼀个对应的64位整数，作为⼀个root id。root id会传递给acker及后续的bolt作为该 消息单元的唯⼀标识。同时⽆论是spout还是bolt每次新⽣成⼀个tuple的时候，都会赋予该tuple⼀ 个64位的整数的id。Spout发射完某个message id对应的源tuple之后，会告知acker⾃⼰发射的root

id及⽣成的那些源tuple的id。⽽bolt呢，每次接受到⼀个输⼊tuple处理完之后，也会告知acker⾃ ⼰处理的输⼊tuple的id及新⽣成的那些tuple的id。Acker只需要对这些id做⼀个简单的异或运算， 就能判断出该root id对应的消息单元是否处理完成了。下⾯通过⼀个图示来说明这个过程。

## Storm的事务拓扑

事务拓扑(transactional topology)是storm0.7引⼊的特性，在最近发布的0.8版本中已经被封装为 Trident，提供了更加便利和直观的接⼝。因为篇幅所限，在此对事务拓扑做⼀个简单的介绍。

事务拓扑的⽬的是为了满⾜对消息处理有着极其严格要求的场景，例如实时计算某个⽤户的成交 笔数，要求结果完全精确，不能多也不能少。Storm的事务拓扑是完全基于它底层的 spout/bolt/acker原语实现的，通过⼀层巧妙的封装得出⼀个优雅的实现。个⼈觉得这也是storm最 ⼤的魅⼒之⼀。

事务拓扑简单来说就是将消息分为⼀个个的批(batch)，同⼀批内的消息以及批与批之间的消息可 以并⾏处理，另⼀⽅⾯，⽤户可以设置某些bolt为committer，storm可以保证committer的 finishBatch()操作是按严格不降序的顺序执⾏的。⽤户可以利⽤这个特性通过简单的编程技巧实现 消息处理的精确。

# Storm在淘宝

由于storm的内核是clojure编写的(不过⼤部分的拓展⼯作都是java编写的)，为我们理解它的实现 带来了⼀定的困难，好在⼤部分情况下storm都⽐较稳定，当然我们也在尽⼒熟悉clojure的世界。 我们在使⽤storm时通常都是选择java语⾔开发应⽤程序。

在淘宝，storm被⼴泛⽤来进⾏实时⽇志处理，出现在实时统计、实时⻛控、实时推荐等场景中。 ⼀般来说，我们从类kafka的metaQ或者基于hbase的timetunnel中读取实时⽇志消息，经过⼀系列 处理，最终将处理结果写⼊到⼀个分布式存储中，提供给应⽤程序访问。我们每天的实时消息量 从⼏百万到⼏⼗亿不等，数据总量达到TB级。对于我们来说，storm往往会配合分布式存储服务⼀ 起使⽤。在我们正在进⾏的个性化搜索实时分析项⽬中，就使⽤了timetunnel + hbase + storm + ups的架构，每天处理⼏⼗亿的⽤户⽇志信息，从⽤户⾏为发⽣到完成分析延迟在秒级。
